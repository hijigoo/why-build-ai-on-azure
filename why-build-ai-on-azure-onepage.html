AI는 세 단계를 거쳐 발전해 왔고, 지금은 세 번째 단계에 들어섰습니다.

  • 1세대 · 예측 AI — 과거 데이터로 미래를 예측합니다. 수요 예측, 고객 이탈 예측이 대표적이며 많은 기업이 이미 보유하고 있습니다.
  • 2세대 · 생성형 AI — 문서 요약, 코드 작성, 대화처럼 콘텐츠를 만들어냅니다. 현재 대부분의 조직이 이 단계에 있습니다.
  • 3세대 · 에이전트 AI — 목표를 주면 스스로 판단하고 도구를 사용해 업무를 완수합니다. 차이의 핵심은 "답을 준다"가 아니라 "일을 끝낸다"입니다.

이 구분이 중요한 이유 — 2세대까지는 사람이 결과를 받아 판단했기 때문에 통제권이 사람에게 있었습니다. 3세대는 에이전트가 사내 시스템을 직접 실행하므로, 신원·권한·감사 체계가 없으면 운영 자체가 성립하지 않습니다. 뒤에서 거버넌스를 비중 있게 다루는 이유가 여기에 있습니다.

디지털 인력(Digital Workforce)
사람 직원처럼 업무를 배정받아 수행하는 에이전트들의 집합을 부르는 표현입니다. 채용·교육·관리의 대상으로 본다는 관점이 담겨 있습니다.

에이전트가 들어오면 사람이 시스템을 조작하던 방식이 뒤집힙니다. 오른쪽 열은 사람이 없어진다는 뜻이 아니라 사람 + 에이전트, 즉 사람이 에이전트의 팀장 역할을 한다는 뜻입니다. 최종 책임과 권한은 계속 사람에게 있습니다.

경영 관점에서 가장 중요한 항목은 '확장성'입니다. 지금까지 업무량 증가에 대응하는 방법은 채용이 거의 유일했습니다. 에이전트는 한 번 잘 만든 패턴을 복제해 확장할 수 있어 비용 곡선의 기울기 자체가 달라집니다. 다만 그 전제는 재사용 가능한 표준 제작·운영 체계이며, 이것이 §6 이후에 다루는 플랫폼의 존재 이유입니다.

RISK 04

규제 리스크

거버넌스 없이 확산되면, 나중에 되돌리는 비용이 지금 준비하는 비용보다 큽니다.

이미 Microsoft 365 · GitHub · Microsoft Fabric을 쓰고 있다면, '지금' 시작하기 가장 가까운 곳은 그 위에 얹히는 Azure입니다.
Part 1 · 신뢰
슬라이드 설명

AI 도입을 미룰 때 생기는 비용은 눈에 잘 보이지 않지만 누적됩니다. 네 가지 형태로 나타납니다.

특히 Shadow AI는 미래의 위험이 아니라 이미 진행 중인 현재의 위험입니다. 회사가 AI를 도입하지 않았다고 해서 AI 리스크가 없는 것이 아니라, 오히려 통제되지 않은 사용만 남습니다. 직원들은 이미 외부 AI 서비스에 사내 문서를 붙여넣고 있습니다.

규제 리스크는 비대칭적입니다. 거버넌스를 나중에 붙이려면 이미 퍼진 에이전트와 데이터 흐름을 되돌려야 하고, 그 비용이 처음부터 설계하는 비용보다 훨씬 큽니다.

Shadow AI
회사의 승인이나 통제 없이 직원이 개인적으로 외부 AI 서비스를 업무에 사용하는 현상입니다. 사내 문서·고객 정보가 외부로 나가도 회사가 알 수 없다는 점이 위험합니다.

02
AI가 우리 비즈니스를 이해하지 못한다

거버넌스가 없다

05
보안 · 규정 준수 리스크
AI가 민감 데이터를 유출할 위험을 사전에 차단할 방법이 필요합니다.

§3 왜 Microsoft인가

"신뢰할 수 있다"를 구체적으로 풀면

01

02
모델 선택의 자유
Microsoft Foundry 모델 카탈로그에서 프론티어(OpenAI)·오픈소스·산업별 모델을 운영 가능한 방식으로 골라 바꿔 씁니다.
03
이미 가진 스택 위에서
Microsoft 365·GitHub·Fabric은 연동 가치로 얹히고, 기준을 실제로 책임지는 엔진은 Azure입니다. 원본을 옮기지 않고 연결부터 시작합니다.
04
AI를 감싸는 보안 · 거버넌스
Entra ID(신원) · Purview(데이터) · Defender(위협) · Agent 365(에이전트 통제 GA 2026.5)가 AI 전 계층을 관통합니다.
Why Build AI on Azure?
슬라이드 설명

"신뢰할 수 있다"는 표현은 그대로 두면 추상적입니다. 실제로 확인 가능한 네 가지 항목으로 바꾸면 위와 같습니다.

①의 표현은 정확히 이해하는 것이 중요합니다. 고객의 입력·출력을 파운데이션 모델 학습에 사용하지 않는다는 원칙이며, 데이터 상주 위치와 약관은 서비스·모델별로 확인이 필요합니다. 이 구분을 정확히 하는 것이 보안·법무 검토에서 오히려 신뢰를 얻는 방법입니다.

②의 실무적 의미 — 모델 종속을 피한다는 것은 단순히 여러 모델이 있다는 뜻이 아니라, 배포·버전 관리·평가·비용 관측 방식은 그대로 둔 채 모델만 교체할 수 있다는 뜻입니다.

Microsoft Entra ID
사람과 시스템의 신원을 확인하고 접근 권한을 관리하는 서비스입니다(옛 Azure Active Directory). 에이전트에게도 사번을 부여하듯 신원을 줄 수 있습니다.
Microsoft Purview
데이터가 어디에 있고 얼마나 민감한지 분류하고, 외부 유출을 막고, 접근 이력을 남기는 데이터 거버넌스 서비스입니다.
Microsoft Defender
공격 시도와 이상 행위를 탐지하고 대응하는 보안 서비스입니다.
Microsoft Agent 365
조직 안의 에이전트를 한곳에서 등록·관리·감사하는 관제 도구입니다. 에이전트의 인사 시스템에 비유할 수 있습니다.
테넌트 격리
클라우드에서 각 고객사의 데이터와 설정이 다른 고객과 논리적으로 분리되어 관리되는 구조를 뜻합니다.

Why Build AI on Azure?
슬라이드 설명

모델 리더십의 실질적 의미는 최신 모델을 먼저 쓸 수 있다가 아니라, 최신 모델을 엔터프라이즈 SLA와 거버넌스 아래에서 쓸 수 있다는 데 있습니다. 연구용으로 좋은 모델과 실제로 운영 가능한 모델은 다릅니다.

실사용 생태계가 근거가 되는 이유 — Microsoft 365 Copilot과 GitHub Copilot은 Microsoft 자신이 대규모로 운영하며 얻은 노하우가 플랫폼에 반영되어 있습니다. 특정 모델(예: 경량 오픈소스 모델)을 선호하는 경우에도 카탈로그에서 해당 모델을 고르고 나머지 운영 체계는 그대로 유지할 수 있습니다.

프론티어 모델(Frontier Model)
현시점에서 성능이 가장 앞선 대형 AI 모델을 가리킵니다. OpenAI의 GPT 계열이 대표적입니다.
모델 카탈로그
사용할 수 있는 AI 모델을 목록으로 모아 두고, 같은 방식으로 배포·관리할 수 있게 한 공간입니다. 업무마다 다른 모델을 골라 쓰고 나중에 교체하기 쉬워집니다.
SLA (Service Level Agreement)
가용성 등 서비스 품질을 사업자가 계약으로 보장하는 수준을 뜻합니다. 업무에 AI를 넣으려면 반드시 확인해야 하는 항목입니다.

Why Build AI on Azure?
슬라이드 설명

AI 도입에서 가장 큰 장벽은 기술이 아니라 신뢰입니다. 위 표의 각 행은 보안·컴플라이언스 검토에서 실제 심사 항목이 되는 내용입니다.

'안전한 AI'가 별도 항목인 이유 — 접근 통제와 위협 탐지 같은 전통적 보안만으로는 AI 고유의 위험을 막지 못합니다. 유해 콘텐츠 생성, 악의적 프롬프트 주입, 우회 시도 같은 문제는 Azure AI Content Safety가 담당합니다. 이 계층이 빠진 채 AI를 구축하는 것이 가장 흔한 실수입니다.

투명성은 평가·추적으로 구현됩니다. Microsoft Foundry의 평가·관측 기능으로 답변의 품질과 비용, 처리 경로를 기록에 남겨 감사 대응의 근거로 사용합니다.

제로 트러스트(Zero Trust)
사내망 안이라도 자동으로 신뢰하지 않고, 접근할 때마다 신원과 권한을 확인하는 보안 원칙입니다.
Azure AI Content Safety
AI가 주고받는 입력과 출력에서 유해 콘텐츠나 공격적 프롬프트를 걸러내는 안전 장치입니다.
DLP (Data Loss Prevention)
민감 정보가 외부로 나가지 못하도록 자동으로 탐지하고 차단하는 기능입니다.
데이터 주권(Data Sovereignty)
데이터가 어느 국가·지역에 저장되고 어느 법의 적용을 받는지에 관한 문제입니다. 금융·공공처럼 규제가 강한 산업에서 특히 중요합니다.

OneLake는 "AI 시대의 OneDrive for Data"로 이해하면 쉽습니다. 파일이 어느 드라이브에 있든 OneDrive에서 하나로 보이듯, 데이터가 어느 시스템에 있든 OneLake에서 하나의 논리적 저장소로 보입니다.

"부서마다 숫자가 다르다"는 문제 — 많은 조직에서 재무팀의 매출과 영업팀의 매출이 다릅니다. 각자 다른 원본과 다른 정의를 쓰기 때문입니다. 이 상태로 AI에게 질문하면 어느 쪽 답을 주더라도 틀린 답이 됩니다. 데이터 통합이 AI의 전제 조건인 이유가 여기에 있습니다.

OneLake는 개방형 포맷(Delta·Parquet)을 사용해 벤더 종속을 최소화합니다. 계층 관점의 상세는 §8 계층 2에서 다룹니다.

슬라이드 설명

이 개념이 자료 전체에서 가장 중요합니다. 모델 접근성은 점점 보편화되지만 우리 회사의 맥락(IQ)은 우리만 만들 수 있고, 그것이 경쟁 우위가 됩니다.

핵심은 세 가지가 합쳐질 때입니다. 데이터(Fabric IQ) + 업무(Work IQ) + 지식(Foundry IQ)이 결합되어야 비로소 "우리 회사를 아는 직원"이 됩니다. 하나만 있으면 여전히 똑똑한 외부인에 머무릅니다.

Fabric IQ
데이터가 무엇을 뜻하는지 아는 지능입니다. "매출", "우량 고객" 같은 용어를 회사 기준대로 해석하게 해줍니다.
Work IQ
일이 어떻게 흘러가는지 아는 지능입니다. 누가 언제 어떤 문서로 협업하는지 같은 업무 맥락을 이해합니다.
Foundry IQ
에이전트가 답변의 근거로 참조할 지식·정책·규정을 다루는 지능입니다. 근거 있는 답변으로 환각을 줄입니다.
온톨로지(Ontology)
업무 용어와 그 관계를 정의해 둔 의미 구조입니다. AI가 데이터를 회사의 언어로 해석하게 하는 사전 역할을 합니다.

에이전트도 소프트웨어이므로 만들고, 테스트하고, 배포하고, 보호해야 합니다. 여기서 중요한 것은 보안이 파이프라인에 내장된다는 점입니다. 나중에 붙이는 보안이 아니라 코드를 올리는 순간부터 작동합니다.

왜 에이전트에 개발 체계가 필요한가 — 에이전트는 프롬프트, 도구 연결, 모델 설정, 평가 기준으로 구성되며 이 모두가 변경 이력을 남겨야 하는 자산입니다. "누가 프롬프트를 바꿔서 응답이 달라졌는가"를 추적할 수 없으면 운영이 불가능합니다.

비밀키 보호가 특히 중요합니다. 에이전트 개발에서는 API 키나 접속 문자열이 코드에 섞이기 쉬운데, 커밋 자체를 차단하는 편이 사후에 키를 교체하는 것보다 훨씬 저렴합니다.

CI/CD
코드 변경을 자동으로 검증하고(CI) 자동으로 배포하는(CD) 방식입니다. 사람이 수동으로 배포할 때 생기는 실수를 줄입니다.
Shift-Left Security
보안 점검을 개발 마지막이 아니라 개발 초기 단계로 앞당기는 접근입니다. 문제를 일찍 발견할수록 수정 비용이 낮습니다.
Secret Protection
비밀번호·API 키 같은 민감 정보가 코드에 포함되면 탐지하고 업로드를 차단하는 GitHub 기능입니다.
Code Security
코드의 취약점과 사용 중인 오픈소스 라이브러리의 보안 문제를 자동으로 검사하는 기능입니다.

이 자료의 목적은 정보 전달이 아니라 다음 논의의 출발점을 만드는 것입니다. 왼쪽 세 질문은 조직의 현재 상태를 확인하는 질문이고, 오른쪽은 그 답을 실행 계획으로 옮기는 방법입니다.

Q1은 대개 그 자리에서 답이 나오고, 그 답이 곧 첫 파일럿 후보가 됩니다. Q2는 데이터 연결 방식(Shortcut·Mirroring·ETL)을 결정하고, Q3은 보안 검토에서 확인해야 할 조건을 미리 드러냅니다.

워크숍 참석자 구성이 결과를 좌우합니다. 업무 오너(무엇을), 데이터 담당(어디에), 보안·컴플라이언스(어떤 조건으로), IT(어떻게) 중 하나라도 빠지면 파일럿 설계가 완성되지 않아 다시 모여야 합니다.

산출물은 두꺼운 제안서가 아니라 파일럿 설계서 한 장입니다. 범위·데이터·보안 요건·성공 기준이 한 장에 담기면 실행 가능성이 크게 올라갑니다.
