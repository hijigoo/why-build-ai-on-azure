슬라이드 설명

이 문서는 GitHub Copilot 을 기능 목록으로 나열하지 않습니다. 네 개의 축으로 나눠서, 각 축에서 무엇을 고를 수 있고 무엇이 GitHub Enterprise Cloud 를 전제로 하는지를 구분합니다. 읽는 대상은 개발 리더와 플랫폼팀입니다.

왜 축으로 나누는가 — 도구 하나하나를 소개하면 "제품이 여섯 개"처럼 들립니다. 실제로는 같은 에이전트를 호출하는 자리가 여섯 개입니다. 축으로 보면 어디까지가 개발자의 선택이고 어디부터가 조직의 결정인지가 드러납니다.

스크롤로 읽고, J·K 로 장을 옮깁니다. 각 장 아래 설명란은 N 으로 전체를 여닫고, 설명 헤더의 접기 버튼으로 장마다 따로 접습니다.

하네스(harness)
모델을 감싸서 실제로 코드를 읽고 고치고 명령을 실행하게 만드는 실행 계층입니다. 같은 모델이라도 어떤 하네스가 구동하느냐에 따라 결과가 달라집니다.
GitHub Enterprise Cloud (GHEC)
GitHub 이 호스팅하는 엔터프라이즈 플랜입니다. 이 문서에서 조직 단위 통제와 클라우드 실행은 대부분 이 플랜을 전제로 합니다.

시작하기 · 아젠다
슬라이드 설명

순서에 의도가 있습니다. 1·2번은 개발자가 직접 고르는 영역이고, 3번부터는 조직이 정하는 영역입니다. 개발자 관심사와 플랫폼·보안·구매 관심사가 갈리는 지점이 2번과 3번 사이입니다.

어디에 시간을 쓸지 — 개발자만 읽는다면 3번은 배경 지식으로 훑어도 됩니다. 반대로 플랫폼·보안·구매 관점이라면 3번이 본론이고 1·2번이 배경입니다. 4번은 실제로 무엇부터 시작할지를 정하는 자리입니다.

약어 표기 — 이 문서는 GHCP 같은 축약을 쓰지 않습니다. GitHub 공식 약어가 아니고, 문서 안에서 뜻이 흔들립니다. 제품명은 GitHub Copilot 으로 씁니다.

추론하는 모델과 실제로 코드를 고치는 하네스는 다른 층입니다. 대부분의 도구는 이 둘을 함께 묶어 팔기 때문에, 모델을 바꾸려면 도구를 바꿔야 하고 에이전트를 바꾸려면 워크플로를 다시 만들어야 합니다.

이 파트는 두 층이 분리되면 무엇이 달라지는지를 다룹니다. 모델은 벤더를 넘나들며 고르고, 하네스는 GitHub Copilot 외에 Claude 와 Codex 까지 같은 화면에서 선택합니다.

허용 범위

Part 1 · 모델과 에이전트
슬라이드 설명

왜 비용 문제인가 — 리팩터링이나 테스트 작성 같은 루틴 작업을 경량 모델로 돌리고 어려운 아키텍처 문제에만 프런티어 모델을 쓰면, 같은 작업량을 훨씬 낮은 비용으로 끝냅니다. 단일 벤더에 묶인 도구에서는 이 최적화 자체가 성립하지 않습니다.

모델명과 단가를 슬라이드에 적지 않은 이유 — 갱신 주기가 짧아 문서가 곧바로 낡습니다. 지원 모델 목록은 docs.github.com 의 supported-models 문서에서 그때그때 확인하는 편이 정확합니다.

과금 단위 — code completion 과 next edit suggestions 는 AI Credits 를 차감하지 않고 유료 플랜에서 사실상 무제한입니다. 에이전트 요청의 과금 단위는 토큰 기반 AI Credits 입니다.

BYOK — 범위를 정확히 — 자체 LLM 키 사용(BYOK)은 VS Code 한정이 아닙니다. 로컬 BYOK 는 VS Code · JetBrains · Xcode · Copilot CLI · GitHub Copilot app · Copilot SDK 에서 지원합니다. 엔터프라이즈 BYOK(서버 측, Preview)는 관리자가 조직 전체에 커스텀 모델을 배포하는 방식이고 Copilot Chat · CLI · IDE 에서 쓰입니다. 다만 플랜에 따라 접근 가능한 모델 범위는 다릅니다.

프런티어 모델
각 벤더의 최상위 성능 모델을 가리킵니다. 성능이 높은 만큼 요청당 비용도 큽니다.
AI Credits
에이전트 요청에 쓰이는 토큰 기반 과금 단위입니다. 조직 단위로 풀링해 관리할 수 있습니다.

슬라이드 설명

GitHub 은 Claude 와 Codex 를 대체하려 하지 않고 플랫폼 안에 하네스로 들였습니다. 개발자는 github.com 의 Agents 화면이나 VS Code 의 Session Target 컨트롤에서 어떤 에이전트로 실행할지 고릅니다.

이미 Claude Code 나 Codex 를 쓰고 있다면 — 그 선택을 버릴 필요가 없습니다. 그대로 쓰되 이슈 관리와 코드 리뷰와 감사 로그가 붙은 상태로 쓰게 됩니다. 기존 CLAUDE.md 와 MCP 설정도 그대로 넘어옵니다.

게이트가 두 단계입니다 — third-party 하네스는 유료 플랜에서 관리자 정책 활성화가 필요합니다. 엔터프라이즈 관리자가 먼저 켜야 조직 관리자에게 설정이 보이고, 그다음 조직 단위로 Claude 와 Codex 를 각각 따로 켭니다. 기본으로 켜져 있지 않습니다. 파일럿 범위를 좁게 잡을 때는 이 구조가 오히려 장점입니다.

정책은 별도이지만 완전히 독립은 아닙니다 — third-party agent 정책과 Copilot cloud agent 정책은 서로 다른 토글입니다. 다만 third-party 에이전트는 cloud agent 가 활성화된 리포지토리와 같은 범위에 접근하므로, 접근 범위를 좁히려면 두 정책을 함께 봐야 합니다.

도입 시점에는 하네스의 Preview 여부와 플랜 조건을 공식 문서로 다시 확인해야 합니다. 성숙도 표기는 이 문서에서 가장 빨리 낡는 항목입니다.

AGENTS.md · CLAUDE.md
에이전트에게 리포지토리의 규칙과 맥락을 알려주는 지시 파일입니다. Anthropic Claude Code 에서 출발한 관례이고 GitHub 은 호환을 지원하는 쪽입니다. GitHub 고유 지시 파일은 copilot-instructions.md 입니다.
MCP (Model Context Protocol)
에이전트에 외부 도구와 데이터 소스를 연결하는 개방 규약입니다.

슬라이드 설명

예전의 gh copilot suggest 확장과는 다른 물건입니다. 명령어를 제안해 주는 도구가 아니라, 파일을 고치고 명령을 실행하고 PR 까지 만드는 에이전트입니다.

성숙도를 정확히 — 샌드박스 기능 전체는 공식 문서에서 public preview 로 안내되지만, 로컬과 클라우드 샌드박스 모두 현재 --experimental 옵션으로 켜야 동작합니다. "클라우드만 실험 기능"이 아니라 둘 다입니다. core CLI 자체는 이와 별개입니다.

클라우드 샌드박스는 조직에서 기본 비활성입니다. 조직이나 엔터프라이즈 설정에서 켜야 구성원이 쓸 수 있고, 정책은 Copilot cloud agent 정책 설정을 그대로 따릅니다. 로컬 샌드박스는 별도 과금이 없고, 클라우드 샌드박스는 사용량 기반으로 과금됩니다.

지시 파일 구분 — AGENTS.md 와 .claude/agents 규약은 Anthropic Claude Code 에서 출발한 관례이고 GitHub 은 호환을 지원하는 쪽입니다. GitHub 고유 지시 파일은 copilot-instructions.md 입니다. 둘을 섞어 쓰면 어느 규약이 적용되는지 헷갈립니다.

hooks
에이전트의 특정 시점(도구 실행 전후 등)에 자동으로 끼어드는 사용자 정의 동작입니다. 정책 검사나 로깅에 씁니다.
샌드박스
호스트와 격리된 실행 환경입니다. 로컬 샌드박스는 파일 시스템·네트워크·자격 증명 접근을 정책으로 제한하고, 클라우드 샌드박스는 GitHub 이 호스팅하는 임시 Linux 환경에서 세션 전체를 돌립니다.

Part 2 · 개발자가 쓰는 도구
슬라이드 설명

인라인 제안과 세 역할은 별개입니다. 왼쪽은 늘 켜져 있고 AI Credits 를 쓰지 않습니다. 오른쪽 세 역할은 필요할 때 골라서 전환합니다. 에이전트를 쓰지 않는 개발자도 손해를 보지 않는 구조입니다.

역할을 나누는 기준 — 코드를 건드리지 않아도 되면 Ask, 바로 고쳐도 되는 작업이면 Agent, 범위가 넓거나 되돌리기 어려우면 Plan 으로 계획을 먼저 확인합니다.

하네스 전환이 일어나는 자리가 여기입니다. Session Target 컨트롤에서 Local · Copilot · Claude · Codex · Cloud 를 바꿉니다. 앞 장의 멀티 하네스가 실제로 손에 잡히는 지점입니다.

용어 — Ask · Agent · Plan 은 VS Code 공식 문서의 built-in agent role 입니다. Local 하네스 세션이 제공하는 기본 역할이고, 세션 도중 agent picker 에서 전환합니다. '에디터 모드' 같은 옛 명칭은 쓰지 않습니다.

혼동하기 쉬운 지점 — GitHub Copilot app 의 Interactive · Plan · Autopilot 은 세션 모드로, VS Code 의 역할과는 다른 층입니다. 이름이 겹치는 Plan 도 서로 다른 개념입니다.

슬라이드 설명

한 사람이 여러 작업을 동시에 굴리는 워크플로를 위한 도구입니다. A 작업이 도는 동안 B 를 시작하고, 둘 다 도는 동안 C 를 리뷰하는 방식이 가능합니다. 작업마다 워크트리가 분리되어 있어 서로 충돌하지 않습니다.

모드는 위험도로 고릅니다 — 되돌리기 쉬운 작업은 Autopilot 으로 맡기고, 범위가 넓거나 영향이 큰 작업은 Plan 으로 계획을 먼저 확인합니다. Interactive 는 한 단계씩 같이 진행할 때 씁니다.

공식 명칭은 GitHub Copilot app 입니다. 'Copilot Desktop' 이라는 이름은 쓰지 않습니다. macOS · Windows · Linux 를 지원합니다.

워크트리(worktree)
같은 리포지토리를 여러 디렉터리에 동시에 체크아웃하는 Git 기능입니다. 브랜치를 오가지 않고 여러 작업을 나란히 진행할 수 있습니다.

자주 나오는 질문 — "자리가 여섯 개면 설정도 여섯 벌 만들어야 하지 않나." 그렇지 않습니다. 지시 파일과 MCP 서버 설정은 리포지토리에 있고, 정책은 조직 설정에 있습니다. 자리가 늘어도 설정은 한 벌입니다.

플랫폼팀 관점 — 새 도구를 도입하면 관리 대상이 하나 늘어납니다. GitHub Copilot 은 이미 관리 중인 GitHub 안에 있어서 통제 체계를 새로 만들 필요가 없습니다. 권한 모델과 감사 로그가 기존 것과 같습니다.

도달 범위가 넓다는 것은 기능 자랑이 아니라 도입 마찰의 문제입니다. 팀마다 쓰는 편집기가 다르면, 도달 범위가 좁은 도구는 일부 팀에만 효과가 있고 나머지는 도구를 하나 더 설치해야 합니다.

Part 3 · 엔터프라이즈
슬라이드 설명

로컬 전용 에이전트는 개발자의 세션에 묶여 있어 노트북을 닫으면 멈춥니다. 그래서 대규모 리팩터링이나 의존성 일괄 업그레이드처럼 오래 걸리는 작업을 맡기기 어렵습니다. 비동기 실행은 이 제약을 없앱니다.

자주 나오는 반론 세 가지

  • 사람 없이 도는데 검증은 누가 하나 — PR 확정 전에 CodeQL, secret scanning, GitHub Advisory Database 기반 의존성 검사를 자동으로 거칩니다. 공식 문서는 이 security validation 에 별도 보안 라이선스가 필요하지 않다고 명시합니다.
  • 소스가 밖으로 나가나 — 조직의 GitHub 안에서 실행되고, 방화벽·네트워크 정책이 샌드박스까지 확장 적용되며, 리포지토리 단위 opt-out 도 가능합니다.
  • CI 비용이 늘지 않나 — 에이전트 코드에 대한 CI 실행 시점을 브랜치 단위로 통제할 수 있습니다.

범위를 정확히 구분해야 합니다. 위 보안 검증은 에이전트 산출물에 대한 사전 검증이지 리포지토리 전체에 대한 상시 code scanning 이 아닙니다. 사설 리포의 상시 스캔과 Security 탭 알림은 GitHub Code Security · GitHub Secret Protection 이 필요합니다. "이제 보안 제품이 필요 없다"는 뜻으로 읽으면 나중에 반드시 문제가 됩니다.

용어 — 이 기능의 이름은 Copilot cloud agent 입니다. Business · Enterprise 플랜에서는 기본 비활성이라 조직이 켜야 합니다.

CodeQL
코드를 질의 가능한 데이터베이스로 만들어 취약점 패턴을 찾아내는 GitHub 의 정적 분석 엔진입니다.
secret scanning
커밋에 API 키·토큰 같은 자격 증명이 섞여 들어갔는지 탐지하는 기능입니다.

독립 에이전트 도구를 쓰면 코드 호스팅과 이슈와 리뷰와 CI 에 각각 연동 작업을 해야 합니다. 그러면 권한 모델이 두 개가 되고 감사 흔적이 두 곳으로 갈라집니다. 규제 산업에서는 이 지점이 도입을 막는 실질적 장애물입니다.

도입 저항을 줄이는 핵심 — 프로세스를 새로 만들 필요가 없다는 점입니다. 지금 쓰는 리뷰 규칙과 CI 게이트가 그대로 에이전트에게도 적용됩니다. 에이전트에게 별도 예외를 주는 구조가 아닙니다.

용어 주의 — 'Agentic DevOps' 는 이 범위를 가리키는 편의상 표현이고, GitHub 공식 제품 문서에서 브랜드 용어로 쓰인다는 근거는 확인되지 않았습니다. 공식 제품명처럼 다루지 않는 편이 안전합니다.

Copilot Autofix

브랜치 보호 규칙

Part 3 · 엔터프라이즈
슬라이드 설명

개발자 설득이 앞에서 끝난다면, 전사 확대 결재는 여기서 납니다. 보안·거버넌스 담당자가 확인하려는 것은 기능 목록이 아니라 통제 지점의 위치입니다.

기본이 닫혀 있다 — MCP 서버는 조직에서 기본 비활성이라 관리자가 명시적으로 켜야 합니다. 보안 검토에서 "기본이 열려 있는가"는 거의 항상 첫 질문이고, 여기서는 닫혀 있는 쪽이 기본값입니다.

지식재산 우려에 대한 1차 답변 — 공개 코드와 일치하는 제안은 Copilot Business 에서 기본 차단됩니다. 파일 단위 content exclusion 으로 특정 경로를 아예 제외할 수도 있습니다.

정책은 층이 나뉩니다 — third-party agent 정책은 cloud agent 정책과 별도 토글이고, 엔터프라이즈에서 먼저 허용해야 조직 설정이 보입니다. 파일럿 범위를 좁게 잡을 때 이 구조를 활용합니다.

확답하기 어려운 항목 — IP 배상의 구체적 범위와 데이터 레지던시는 약관·계약 조건에 달려 있어 문서만으로 단정할 수 없습니다. 도입 검토 시 법무 확인이 필요한 항목으로 따로 분류하는 편이 안전합니다.

용어 — 관리자 문맥에서는 AI Controls 를 씁니다. 'Agent HQ' 는 공식 문서에 등장하지 않는 표현이고, 그 안의 UI 라벨은 Agents 탭입니다.

content exclusion
지정한 파일이나 경로를 Copilot 이 아예 읽지 못하게 제외하는 설정입니다. 민감 코드 경로에 씁니다.

슬라이드 설명

이 장이 문서 전체의 신뢰를 만듭니다. 불리한 사실을 먼저 꺼내기 때문에 앞의 내용이 믿을 만해집니다. 특히 기술 청중에게 그렇습니다.

기본값에 주의 — Copilot cloud agent 는 GA 이지만 Business · Enterprise 플랜에서는 기본 비활성입니다. 멀티 하네스도 관리자가 정책을 켜야 동작합니다. "구매하면 바로 켜져 있다"가 아닙니다.

GHES 를 쓰고 있다면 — 공식 문서가 Copilot 미지원을 명시하므로 이 문서의 내용을 현재 제공 가능한 것으로 받아들이면 안 됩니다. 도구와 모델 축은 지금 플랜에서 쓸 수 있지만, 클라우드 실행과 조직 단위 통제는 GHEC 위에서 성립합니다. 전부 옮겨야 한다는 뜻은 아니고, 어느 범위부터 옮길지를 설계하는 것이 현실적인 출발점입니다.

확인되지 않은 항목 — GHES 3.22 의 에어갭 GitHub Copilot CLI technical preview 는 공식 문서에서 확인되지 않았습니다. 이 문서에서는 다루지 않습니다.

GHEC · GHES
GHEC 는 GitHub 이 호스팅하는 엔터프라이즈 플랜, GHES 는 고객이 자체 인프라에 설치해 운영하는 서버 제품입니다.

좌석을 배포한 다음 날 조직이 달라지지 않는 이유는 도구가 부족해서가 아닙니다. 일하는 방식과 검토 기준이 함께 바뀌지 않았기 때문입니다. 워크샵은 그 전환을 설계하는 자리입니다.

W4 는 전제 조건이 있습니다 — GitHub Enterprise Cloud 를 전제로 합니다. 클라우드 실행과 조직 단위 거버넌스를 실제로 걸어보는 과정이기 때문입니다. GHES 환경이라면 W1~W3 까지 진행하고 W4 는 전환 로드맵과 함께 논의합니다.

각 워크샵의 상세 커리큘럼은 별도 오퍼링 패키지 문서에 있습니다. 이 문서에서는 이름과 대상까지만 다룹니다.

슬라이드 설명

하루로 약속할 수 있는 범위 — 기준선, 챔피언 명단, 다음 단계 합의까지입니다. 사용 품질이나 사업 성과는 하루 워크샵으로 약속할 수 있는 것이 아닙니다.

단일 수치를 단정하지 않습니다. "생산성 몇 퍼센트 향상" 같은 표현은 조직·언어·코드베이스에 따라 편차가 커서 그대로 옮길 수 없습니다. 각 조직에서 합의한 기준선 대비 개선폭을 측정하는 편이 정확합니다.

측정 지표는 단계별로 다릅니다

  • 도입 4주 — 좌석 대비 활성 사용률
  • 12주 — 제안 수용률, agent sessions 성공률
  • 3개월 이후 — PR 라이프사이클, DORA 4 metrics

워크샵은 이 측정의 출발점을 만드는 자리입니다. 기준선 없이 시작하면 나중에 효과를 증명할 방법이 없습니다.

DORA 4 metrics
배포 빈도, 변경 리드 타임, 변경 실패율, 복구 시간. 소프트웨어 전달 성능을 재는 업계 표준 지표입니다.

마무리
슬라이드 설명

네 개 축을 관통하는 메시지는 하나입니다. 선택을 강요하지 않는다는 것입니다. 쓰던 모델과 에이전트와 편집기를 그대로 두고, 그 위에 조직이 통제하는 한 겹을 덮습니다.

세 가지 확인 항목이 왜 그 순서인가

  • GHEC / GHES — 제공 가능 범위의 상한이 여기서 정해집니다. W4 가능 여부도 같이 결정됩니다.
  • 대상 직군 — 비개발자 중심이면 W2, 개발자 중심이면 W3 로 시작합니다.
  • 감사 · 정책 요건 — 규제 산업이면 거버넌스 논의를 뒤로 미루지 않고 1일차로 당깁니다.

확인하기 좋은 순서 — ① 쓰던 모델을 GitHub Copilot 하네스에서 그대로 실행 ② 같은 과업을 다른 모델로 한 번 더 실행해 비교 ③ 이슈 할당에서 cloud agent 를 거쳐 PR 생성까지 비동기 실행 ④ AI Controls 정책 화면. ①에서 "그대로 되는구나"가 확인되면 대부분의 의문이 한꺼번에 해소됩니다.

성숙도는 다시 확인해야 합니다. 이 문서의 GA · Preview · Experimental 표기는 2026-08-26 기준입니다. 도입 시점에는 docs.github.com 에서 다시 확인하세요. 이 문서에서 가장 빨리 낡는 항목입니다.
