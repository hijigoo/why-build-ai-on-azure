# Part 1 — 모델과 에이전트
*무엇으로 추론하고, 무엇이 실행하는가*

## 1. 멀티 모델 — 여러 벤더의 모델을 같은 인터페이스에서 고릅니다

모델이 추가되거나 바뀌어도 도구와 워크플로는 그대로입니다.

- **복수 벤더** — OpenAI · Anthropic · Google · xAI · Microsoft 모델이 한 구독에 들어옵니다.
- **자동 선택** — 과업에 맞는 모델을 자동 지정하고, 자동 선택 사용 시 모델 비용이 할인됩니다.
- **과업별 배분** — 루틴 작업은 경량 모델로, 어려운 문제에만 프런티어 모델을 씁니다.
- **허용 범위** — 사용 가능한 모델은 개발자가 아니라 관리자 정책이 정합니다.

> 🎙 모델 선택권은 성능 문제이면서 동시에 비용 문제입니다. 리팩터링·테스트 작성 같은 루틴 작업을 경량 모델로 돌리고 어려운 아키텍처 문제에만 프런티어 모델을 쓰면 같은 작업량을 훨씬 낮은 비용으로 끝냅니다. 단일 벤더 도구에서는 이 최적화 자체가 성립하지 않습니다.
>
> **슬라이드에 모델명·단가를 넣지 않은 이유** — 갱신 주기가 짧아 덱이 즉시 낡습니다. 최신 목록은 `docs.github.com` 의 supported-models 문서를 그 자리에서 띄우세요.
>
> **비용 질문 1차 방어선** — code completion 과 next edit suggestions 는 GitHub AI Credits 를 차감하지 않고 유료 플랜에서 사실상 무제한입니다. 과금 단위는 토큰 기반 AI Credits 이고, "월 300 premium requests" 같은 옛 표현은 쓰지 마세요.
>
> ⚠️ **범위를 정확히** — BYOK 는 VS Code 한정이 아닙니다. 로컬 BYOK 는 VS Code · JetBrains · Xcode · Copilot CLI · GitHub Copilot app · Copilot SDK 에서 지원하고, 엔터프라이즈 BYOK(서버 측)는 public preview 입니다. 다만 플랜에 따라 접근 가능한 모델 범위가 다릅니다.

## 2. 멀티 하네스 — Claude와 Codex를 GitHub 안에서 실행합니다

모델뿐 아니라 에이전트도 고릅니다. 같은 화면에서 전환합니다.

- **하네스 선택** — Copilot · Claude · Codex 를 같은 화면에서 고릅니다. `Preview`
- **병렬 실행** — 한 과업을 여러 에이전트에 동시에 할당합니다.
- **결과 비교** — 접근 방식을 비교한 뒤 채택할 것만 고릅니다.
- **자산 이관** — CLAUDE.md · AGENTS.md · MCP 서버 설정이 그대로 넘어옵니다.

> 🎙 이 덱에서 가장 인상이 강한 슬라이드입니다. GitHub 은 Claude 와 Codex 를 대체하려 하지 않고 플랫폼 안에 하네스로 들였습니다. 개발자는 github.com 의 Agents 화면이나 VS Code 의 Session Target 컨트롤에서 어떤 에이전트로 실행할지 고릅니다.
>
> **이미 Claude Code 나 Codex 를 쓰는 고객이라면** — "그 선택을 버리실 필요가 없습니다. 그대로 쓰시되 이슈 관리와 코드 리뷰와 감사 로그가 붙은 상태로 쓰시게 되는 겁니다."
>
> ⚠️ **정확히 말할 것** — Claude · Codex 하네스는 public preview 이고 유료 플랜에서 관리자 정책 활성화가 필요합니다. **게이트가 두 단계**입니다. 엔터프라이즈 관리자가 먼저 켜야 조직 관리자에게 설정이 보이고, 그다음 조직 단위로 Claude 와 Codex 를 각각 따로 켭니다. 파일럿 범위를 좁게 잡을 때 이 구조가 오히려 장점입니다.
> Copilot cloud agent 를 꺼도 third-party agent 는 자동으로 꺼지지 않습니다(정책 별도). Google Jules · Cognition Devin 은 예정 발표만 있습니다. '이너 하네스' 같은 비공식 변형은 쓰지 않습니다.

# Part 2 — 개발자가 쓰는 도구
*터미널 · 편집기 · 데스크톱 앱 · 웹 · 모바일*

## 3-1. GitHub Copilot CLI — 터미널에서 그대로

터미널을 벗어나지 않는 개발자를 위한 에이전트입니다. 전 플랜 포함.

- **도구 연결** — 로컬·원격 MCP 서버를 붙입니다. GitHub MCP Server 가 내장되어 있습니다.
- **확장** — custom agents · agent skills · hooks · 커스텀 지시를 지원합니다.
- **plan 모드** — 먼저 계획을 세우고 승인을 받은 뒤 실행하도록 전환할 수 있습니다. `core CLI GA`
- **샌드박스 실행** — 로컬 또는 클라우드의 격리된 환경에서 실행합니다. `Experimental`

> 🎙 이전의 `gh copilot suggest` 확장과는 다른 물건입니다. 잘 먹히는 대상은 CI/CD 자동화를 많이 하는 플랫폼 엔지니어, 서버에 SSH 로 붙어 일하는 인프라 팀, IDE 를 안 쓰는 시니어 개발자입니다.
>
> ⚠️ **성숙도를 정확히** — 샌드박스 기능 전체는 공식 문서에서 public preview 로 안내되지만, **로컬과 클라우드 샌드박스 모두 `--experimental` 옵션으로 켜야 동작합니다.** "클라우드만 실험 기능"이 아닙니다. 클라우드 샌드박스는 조직·엔터프라이즈 설정에서 기본 비활성이고, 정책은 Copilot cloud agent 정책을 그대로 따릅니다. 로컬 샌드박스는 추가 과금이 없고 클라우드 샌드박스는 사용량 기반 과금입니다.
>
> ⚠️ **정확히 구분할 것** — AGENTS.md 와 `.claude/agents` 규약은 Anthropic Claude Code 에서 출발한 관례이고 GitHub 은 호환을 지원하는 쪽입니다. "AGENTS.md 는 GitHub 기능입니다" 라고 말하면 기술 청중에게 바로 신뢰를 잃습니다. GitHub 고유 지시 파일은 `copilot-instructions.md` 입니다.

## 3-2. VS Code — 편집기 기본 기능과 에이전트를 함께

인라인 제안은 계속 쓰면서, 필요할 때만 에이전트로 전환합니다.

- **인라인 제안** — code completion 과 next edit suggestions. AI Credits 를 차감하지 않습니다.
- **Ask 역할** — 코드를 바꾸지 않고 질문에 답하고 설명합니다.
- **Agent 역할** — 파일을 편집하고 명령을 실행하며 결과를 보고 스스로 반복합니다.
- **Plan 역할** — 먼저 조사해서 구현 계획을 만든 뒤 승인을 받습니다.

> 🎙 ⚠️ **용어를 반드시 지킬 것** — VS Code 의 현재 공식 표현은 Ask · Agent · Plan **'역할(role)'** 입니다. '에디터 모드' 나 '에이전트 모드' 같은 옛 명칭은 쓰지 마세요. Edit mode 는 현재 문서에서 별도 모드로 존재하지 않습니다.
>
> **비용 대화에서 중요** — 인라인 제안은 이 세 역할과 별개이고 AI Credits 를 차감하지 않습니다. "에이전트를 안 쓰는 개발자도 손해가 아니다" 라는 논리로 쓰세요.
>
> 하네스 전환이 실제로 일어나는 자리가 여기입니다. Session Target 컨트롤에서 Local · Copilot · Claude · Codex · Cloud 를 바꿉니다.

## 3-3. GitHub Copilot app — 세션을 병렬로 돌립니다

에이전트 기반 개발 전용 데스크톱 앱입니다. 전 플랜 포함.

- **병렬 세션** — 여러 작업을 각각 별도 브랜치·워크트리에서 동시에 진행합니다.
- **세 가지 모드** — Interactive 협업 · Plan 승인 후 실행 · Autopilot 자율.
- **GitHub 통합** — 이슈 확인, PR 생성·리뷰, CI 상태까지 앱 안에서 처리합니다.
- **예약 작업** — automations 로 반복 작업을 예약해 둘 수 있습니다.

> 🎙 한 사람이 여러 작업을 동시에 굴리는 워크플로를 위한 도구입니다. A 작업이 도는 동안 B 를 시작하고 둘 다 도는 동안 C 를 리뷰하는 방식이 가능합니다. 세션 모드는 위험도에 따라 고르는 것이 실무 패턴입니다. macOS · Windows · Linux 지원.
>
> ⚠️ 공식 명칭은 **GitHub Copilot app** 입니다. 'Copilot Desktop' 이 아닙니다.

## 3-4. 도달 범위 — 개발자가 이미 있는 자리에서 호출합니다

제품이 여섯 개가 아니라, 같은 에이전트를 호출하는 자리가 여섯 개입니다.

| 도구 | 무엇을 하는가 |
|---|---|
| **GitHub Copilot CLI** | 터미널에서 코드 수정과 PR 생성까지 |
| **VS Code · Visual Studio** | 인라인 제안 + Ask · Agent · Plan 역할 |
| **JetBrains · Eclipse · Xcode · Neovim** | 주요 IDE 전반에서 동일하게 사용 |
| **GitHub Copilot app** | 브랜치별 병렬 세션과 PR 라이프사이클 관리 |
| **github.com** | 이슈 할당, PR 코멘트로 에이전트 호출 |
| **GitHub Mobile** | 이동 중 진행 상황 확인과 지시 |

> 🎙 개발 조직이 한 가지 도구만 쓰는 경우는 드뭅니다. 닷넷 팀은 Visual Studio, 자바 팀은 JetBrains, iOS 팀은 Xcode, 인프라 팀은 Neovim 이나 터미널을 씁니다. 도달 범위가 좁으면 일부 팀만 혜택을 보고 나머지는 도구를 하나 더 설치해야 합니다.
>
> **반드시 나오는 질문** — "도구가 여섯 개면 설정도 여섯 벌 만들어야 하지 않냐." 아닙니다. 다음 슬라이드가 그 답입니다.
>
> **플랫폼팀에 잘 먹힘** — 새 도구를 도입하면 관리 대상이 하나 늘어나는데 GitHub Copilot 은 이미 관리 중인 GitHub 안에 있어서 새로 통제 체계를 만들 필요가 없습니다.

# Part 3 — 엔터프라이즈
*GitHub Enterprise Cloud 위에서 성립하는 것들*

## 4. 비동기 실행 — 사람이 접속해 있지 않아도 실행이 계속됩니다

클라우드 실행은 GitHub Actions 기반 임시 환경에서 이루어집니다.

```
이슈 할당 → 조사 · 계획 → 브랜치 수정 → 보안 검증 → PR · 사람 리뷰
```

**에이전트가 만든 코드는 PR 확정 전에 CodeQL · secret scanning · 의존성 검사를 자동으로 거칩니다. 이 사전 검증에는 별도 보안 라이선스가 필요하지 않습니다.**

> 🎙 GitHub Enterprise Cloud 업셀의 실질적 근거입니다. 로컬 전용 에이전트는 개발자의 세션에 묶여서 노트북을 닫으면 멈춥니다. 그래서 대규모 리팩터링이나 의존성 일괄 업그레이드 같은 장시간 작업을 맡기기 어렵습니다.
>
> **반드시 나오는 반론 3가지**
> 1. *사람 없이 도는데 검증은 누가 하느냐* — PR 확정 전에 CodeQL, secret scanning, GitHub Advisory Database 기반 의존성 검사를 자동으로 거칩니다. 공식 문서는 이 security validation 에 별도 보안 라이선스가 필요하지 않다고 명시합니다.
>    ⚠️ **범위를 정확히 말하세요.** 이건 에이전트 산출물에 대한 **사전 검증**이지 리포지토리 전체에 대한 상시 code scanning 이 아닙니다. 사설 리포의 상시 스캔과 Security 탭 알림은 **GitHub Code Security · GitHub Secret Protection** 이 필요합니다. "이제 보안 제품 안 사도 된다" 로 들리게 말하면 나중에 반드시 문제가 됩니다.
> 2. *소스가 밖으로 나가느냐* — 조직의 GitHub 안에서 실행되고 방화벽·네트워크 정책이 샌드박스까지 확장 적용되며 리포지토리 단위 opt-out 도 가능합니다.
> 3. *CI 비용이 늘지 않느냐* — 에이전트 코드에 대한 CI 실행 시점을 브랜치 단위로 통제할 수 있습니다.
>
> ⚠️ 샌드박스는 public preview. '앰비언트 에이전트' 는 공식 용어가 아니니 **Copilot cloud agent** 로 부르세요.

## 5. SDLC 통합 — 계획부터 운영까지 한 플랫폼에서 이어집니다

| SDLC 구간 | GitHub 기능 | 에이전트가 하는 일 |
|---|---|---|
| 계획 | Issues + Planning Agent | 요구사항을 작업 단위로 분해 |
| 코딩 | Agent Mode + Cloud Agent | 브랜치에서 수정하고 PR 생성 |
| 리뷰 | Copilot Code Review | PR 1차 검토와 수정 제안 |
| 테스트 · 보안 | Code Security + Copilot Autofix | 취약점 탐지와 수정안 제시 |
| 배포 · 운영 | Actions + Agentic Workflows | 반복 작업을 자연어 지시로 실행 |

**에이전트가 만든 PR 도 기존 브랜치 보호 규칙과 CI 를 그대로 통과해야 머지됩니다.**

> 🎙 독립 에이전트 도구는 코드 호스팅과 이슈와 리뷰와 CI 에 연동 작업을 따로 해야 하고, 그러면 권한 모델이 두 개가 되고 감사 흔적이 두 곳으로 갈라집니다.
>
> **도입 저항을 크게 줄이는 문장** — "프로세스를 새로 만드실 필요가 없습니다. 지금 쓰시는 리뷰 규칙과 CI 게이트가 그대로 에이전트에게도 적용됩니다."
>
> ⚠️ **'Agentic DevOps'** 는 우리 오퍼링에서 범위를 가리키는 명칭으로 쓰지만, GitHub 공식 제품 문서에서 브랜드 용어로 쓰인다는 근거는 확인되지 않았습니다. 고객 앞에서 공식 제품명처럼 말하지 마세요.

## 6. 거버넌스 — 모델 · 에이전트 · MCP 를 조직 정책으로 통제합니다

엔터프라이즈 설정의 AI Controls 에서 한 곳으로 관리합니다.

- **중앙 정책** — 엔터프라이즈 일괄 적용 또는 조직 소유자에게 위임.
- **허용 범위** — MCP 서버는 조직에서 기본 비활성. 명시적으로 켜야 합니다.
- **감사** — 에이전트 활동이 전용 감사 이벤트로 남습니다.
- **비용** — AI Credits 를 조직 단위로 풀링·관리합니다.

> 🎙 보안·거버넌스 담당자가 참석한 자리라면 여기에 가장 많은 시간을 쓰세요. 개발자 설득은 앞에서 끝났고 전사 확대 결재는 여기서 납니다.
>
> **보안팀에 잘 먹히는 디테일** — MCP 서버는 기본 비활성이라 명시적으로 켜야 하는데, "기본이 열려 있는 게 아니라 닫혀 있다"는 점이 특히 잘 먹힙니다. 공개 코드와 일치하는 제안은 Copilot Business 에서 기본 차단이고 지식재산 우려에 대한 1차 답변으로 쓰세요. third-party agent 정책은 cloud agent 정책과 별도입니다. 파일 단위 content exclusion 으로 특정 경로를 아예 제외할 수도 있습니다.
>
> ⚠️ **그 자리에서 단정하지 말 것** — IP 배상의 구체적 범위, 데이터 레지던시. 법무·약관 확인 후 회신한다고 답하세요.
> 용어는 **AI Controls** 를 쓰고 'Agent HQ' 는 발표·마케팅 표현이라 관리자 문맥에서는 쓰지 않습니다.

>
> **"그럼 GHEC 로 옮겨야 하나요?"** — "전부 옮기셔야 한다는 뜻은 아닙니다. 도구와 모델 축은 지금 플랜에서 바로 쓰실 수 있고, 다만 클라우드 실행과 조직 단위 통제가 GHEC 위에서 성립합니다. 어느 범위부터 옮길지를 같이 설계하는 게 현실적인 출발점입니다."

# Part 4 — 오퍼링 워크샵
*하루짜리 워크샵 네 가지*

## 8. 조직의 어느 지점을 먼저 움직일지 고릅니다

네 가지 모두 **하루 과정**입니다. 순서대로 밟을 수도, 필요한 것만 고를 수도 있습니다.

| | 워크샵 | 대상 | 무엇을 하는가 |
|---|---|---|---|
| **W1** | **개발 문화와 프로세스 자동화** | C-Level · 개발 임원 | AI 도입이 조직의 어느 프로세스를 바꾸는지 정리하고, 투자 우선순위와 성과 지표를 합의합니다 |
| **W2** | **비개발 직군을 위한 GitHub Copilot** | 기획 · 마케팅 · 운영 | 문서·데이터·반복 업무에 Copilot 을 적용해 봅니다. 개발 지식 없이 따라올 수 있는 구성입니다 |
| **W3** | **개발자를 위한 GitHub Copilot** | 개발자 | 자동완성 단계를 넘어 에이전트 활용까지 끌어올립니다. 팀의 실제 리포지토리로 진행합니다 |
| **W4** | **Agentic SDLC 완전 적용** | 시니어 개발자 · 플랫폼팀 | 이슈에서 배포까지 한 바퀴를 에이전트와 함께 돌리고, 거버넌스 정책을 같이 겁니다 |

> 🎙 여기서 파는 것은 라이선스가 아니라 **정착**입니다. 좌석을 배포한 다음 날 조직이 달라지지 않는 이유는 도구가 부족해서가 아니라 일하는 방식과 검토 기준이 함께 바뀌지 않았기 때문입니다.
>
> **네 가지를 다 하시라고 권하지 마세요.** 고객의 현재 상태를 먼저 물어보고 하나를 지목하는 편이 훨씬 잘 팔립니다. 다음 슬라이드가 그 기준입니다.
>
> W4 는 GitHub Enterprise Cloud 가 전제입니다. GHES 고객에게는 W1~W3 까지만 제안하고 W4 는 전환 로드맵과 함께 논의합니다.

## 9. 어느 워크샵부터 시작하나

| 고객의 현재 상태 | 시작 | 다음 |
|---|---|---|
| 도입 여부를 아직 결정하지 못했다 | **W1** 경영진 세션 | 대상 직군에 따라 W2 또는 W3 |
| 좌석은 샀는데 개발팀만 쓰고 있다 | **W2** 비개발 직군 | 전사 확산 계획 수립 |
| 개발자가 자동완성 수준에서 멈춰 있다 | **W3** 개발자 | 성과 확인 후 W4 |
| 이미 잘 쓰는 팀이 있고 조직 표준을 만들고 싶다 | **W4** Agentic SDLC | 거버넌스 정착 · 확산 |
| GitHub Enterprise Server 를 쓰고 있다 | **W1 · W2 · W3** | W4 는 GHEC 전환 로드맵과 함께 |

**공통 산출물** — 팀 표준 초안 · 측정 기준선 · 다음 단계 합의

> 🎙 이 표가 이 덱에서 **가장 실용적인 슬라이드**입니다. 고객이 자기 상태를 말하면 그 자리에서 한 줄을 짚으면 됩니다.
>
> **기간별로 약속 가능한 것** — 하루 워크샵으로 약속할 수 있는 것은 *기준선 · 챔피언 명단 · 다음 단계 합의*까지입니다. 사용 품질이나 사업 성과는 하루로 약속하지 마세요. "생산성 55% 향상" 같은 단일 수치는 절대 단정하지 않습니다. 고객사 파일럿에서 합의된 기준선 대비 개선폭을 측정하겠다고 말하세요.
>
> **측정 지표는 단계별로** — 도입 4주는 좌석 대비 활성 사용률, 12주는 제안 수용률과 agent sessions 성공률, 3개월 이후에 PR 라이프사이클과 DORA 4 metrics 를 봅니다. 워크샵은 이 측정의 출발점을 만드는 자리입니다.
>
> 각 워크샵의 상세 커리큘럼은 오퍼링 패키지 문서(P1 · P2 · P5 · P6)에 있습니다. 이 덱에서는 이름과 대상까지만 말하고, 상세는 별도 자료로 넘깁니다.

## 마무리

> **모델도 에이전트도 도구도 고르지 않아도 됩니다.
> 조직이 통제하는 한 겹만 위에 덮습니다.**

**다음 미팅에서 확인할 세 가지**

1. **GHEC / GHES** — 제공 가능 범위의 상한, 그리고 W4 가능 여부가 여기서 결정됩니다.
2. **대상 직군** — 비개발자 중심이면 W2, 개발자 중심이면 W3 로 시작합니다.
3. **감사 · 정책 요건** — 규제 산업이면 거버넌스를 워크샵 1일차로 당깁니다.

*다음 단계: 고객 리포지토리 1개로 하네스 전환과 이슈에서 PR 까지를 시연하고, 그 자리에서 워크샵 한 가지를 지목합니다.*

> 🎙 계약을 파는 슬라이드가 아니라 **다음 미팅과 워크샵 한 가지**를 파는 슬라이드입니다.
>
> **데모 순서** — ① 고객이 쓰던 모델을 GitHub Copilot 하네스에서 실행 ② 같은 과업을 다른 모델로 한 번 더 실행해서 비교 ③ 이슈 할당 → cloud agent → PR 생성까지 비동기 실행 ④ AI Controls 정책 화면.
> ①이 가장 중요합니다. "정말 그대로 되네"를 눈으로 보여주는 순간 대부분의 반론이 한꺼번에 해소됩니다. 데모 계정의 하네스와 cloud agent 정책이 미리 켜져 있는지 확인하세요.
>
> ⚠️ 가격을 먼저 꺼내지 마세요. 고객이 물으면 플랜 경계로 돌아가 어느 범위부터 시작할지를 먼저 합의한 뒤 견적을 잡겠다고 답하세요.
>
> 워크샵 상세 커리큘럼은 [오퍼링 패키지 문서](../../README.md#6개-대표-패키지)로 넘깁니다.
