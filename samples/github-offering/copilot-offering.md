# Part 1 — 모델과 에이전트
*모델도 에이전트도 **벤더에 묶이지** 않습니다*

## 1. 한 구독으로 **여러 벤더**의 모델을 사용합니다

모델이 추가되거나 바뀌어도 도구와 워크플로는 그대로입니다.

- **복수 벤더** — OpenAI · Anthropic · Google · xAI · Microsoft 등 여러 벤더가 한 구독에 들어옵니다.
- **자동 선택** — 과업에 맞는 모델을 자동 지정하고, 자동 선택 사용 시 모델 비용이 할인됩니다.
- **과업별 배분** — 루틴 작업은 경량 모델로, 어려운 문제에만 프런티어 모델을 씁니다.
- **허용 범위** — 사용 가능한 모델은 개발자가 아니라 관리자 정책이 정합니다.

> 🎙 모델 선택권은 성능 문제이면서 동시에 비용 문제입니다. 리팩터링·테스트 작성 같은 루틴 작업을 경량 모델로 돌리고 어려운 아키텍처 문제에만 프런티어 모델을 쓰면 같은 작업량을 훨씬 낮은 비용으로 끝냅니다. 단일 벤더 도구에서는 이 최적화 자체가 성립하지 않습니다.
>
> **슬라이드에 모델명·단가·벤더 수를 넣지 않은 이유** — 갱신 주기가 짧아 덱이 즉시 낡습니다. 벤더가 추가되거나 빠지면 "다섯 벤더" 같은 숫자는 그 자리에서 틀린 말이 됩니다. 최신 목록은 `docs.github.com` 의 supported-models 문서를 그 자리에서 띄우세요.
> 슬라이드의 벤더 나열도 예시입니다. "이게 전부입니다" 로 말하지 마세요.
>
> **비용 질문 1차 방어선** — code completion 과 next edit suggestions 는 GitHub AI Credits 를 차감하지 않고 유료 플랜에서 사실상 무제한입니다. 과금 단위는 토큰 기반 AI Credits 이고, "월 300 premium requests" 같은 옛 표현은 쓰지 마세요.
>
> ⚠️ **과장 금지** — BYOK 는 현재 VS Code 한정. 플랜에 따라 접근 가능한 모델 범위가 다름.

## 2. 사용하시던 **Claude · Codex** 를 그대로 사용합니다

모델뿐 아니라 에이전트도 고릅니다. 같은 화면에서 전환합니다.

- **하네스 선택** — Copilot · Claude · Codex 를 같은 화면에서 고릅니다. `Preview`
- **병렬 실행** — 한 과업을 여러 에이전트에 동시에 할당합니다.
- **결과 비교** — 접근 방식을 비교한 뒤 채택할 것만 고릅니다.
- **자산 이관** — CLAUDE.md · AGENTS.md · MCP 서버 설정이 그대로 넘어옵니다.

**셋을 함께 쓰면**

> **세 에이전트가 한 구독 · 한 정책 안에 있습니다**
> 벤더마다 따로 계약하고 따로 통제하지 않습니다. 어느 에이전트로 실행하든 이슈 · 리뷰 · 감사는 같은 자리에 남습니다.

한 벤더의 성능 변화나 장애가 **개발 속도를 좌우하지 않습니다**.

**디자인 메모** · 오른쪽 상자는 두 번 바뀌었습니다. 처음에는 `"그 선택을 버리실 필요가 없습니다"` 라는
**안심시키는 말**이었고(안심은 반론을 막을 뿐 구매 이유가 되지 못합니다), 다음에는 `두 갈래로 돌립니다` 라는
**병렬 실행의 이득**이었습니다. 후자의 문제는 왼쪽 `02 병렬 실행` · `03 결과 비교` 와 같은 말을 반복한다는 점,
그리고 **셋 중 둘만 세는 것처럼** 들린다는 점이었습니다.

지금은 `Copilot · Claude · Codex` **셋이 한 구독과 한 정책 안에 있다**는 사실을 말합니다.
보통은 벤더별로 계약이 갈리고, 관리 화면이 하나씩 늘고, 감사 로그도 따로 남습니다.
**고를 수 있다**가 아니라 **고르는데도 관리가 늘지 않는다**가 이 슬라이드의 값입니다.

> 🎙 이 덱에서 가장 인상이 강한 슬라이드입니다. GitHub 은 Claude 와 Codex 를 대체하려 하지 않고 플랫폼 안에 하네스로 들였습니다. 개발자는 github.com 의 Agents 화면이나 VS Code 의 Session Target 컨트롤에서 어떤 에이전트로 실행할지 고릅니다.
>
> **셋을 함께 쓰면 — 오른쪽 상자의 결론**
> 여기서 파는 것은 셋을 **고를 수 있다**는 사실이 아니라, 셋이 **한 구독과 한 정책 안에** 들어와 있다는 사실입니다. 보통은 벤더별로 계약을 따로 하고, 관리 화면이 따로 생기고, 감사 로그도 따로 남습니다. 여기서는 에이전트를 바꿔도 이슈와 PR, 리뷰 규칙, 감사 기록이 같은 자리에 그대로 남습니다.
>
> **역할별로 이렇게 말하세요**
> - *개발 리더* — 팀마다 선호하는 에이전트가 달라도 강제로 통일시키지 않아도 됩니다.
> - *구매* — 벤더가 늘어도 계약과 청구가 하나로 유지됩니다.
> - *보안* — 에이전트가 늘어도 정책과 감사 지점이 하나입니다.
>
> 아래 한 줄은 리스크 이야기입니다. 특정 벤더의 성능이 흔들리거나 장애가 나도 개발 속도가 그대로입니다.
>
> ⚠️ **"세 에이전트를 한 곳에서 쓸 수 있는 건 GitHub 뿐" 이라고 단정하지 마세요.** 경쟁 제품의 현재 상태를 우리가 보증할 수 없습니다. 우리가 무엇을 하는지만 말하면 차이는 고객이 알아서 읽습니다.
> ⚠️ **"두 배 빨라진다" 로 말하지 마세요.** 병렬 실행의 효과는 속도가 아니라 **선택지**입니다.
>
> **이미 Claude Code 나 Codex 를 쓰는 고객이라면** — "그 선택을 버리실 필요가 없습니다. 그대로 쓰시되 이슈 관리와 코드 리뷰와 감사 로그가 붙은 상태로 쓰시게 되는 겁니다."
>
> ⚠️ **정확히 말할 것** — Claude · Codex 하네스는 public preview 이고 유료 플랜에서 관리자 정책 활성화가 필요합니다. **게이트가 두 단계**입니다. 엔터프라이즈 관리자가 먼저 켜야 조직 관리자에게 설정이 보이고, 그다음 조직 단위로 Claude 와 Codex 를 각각 따로 켭니다. 파일럿 범위를 좁게 잡을 때 이 구조가 오히려 장점입니다.
> Copilot cloud agent 를 꺼도 third-party agent 는 자동으로 꺼지지 않습니다(정책 별도). Google Jules · Cognition Devin 은 예정 발표만 있습니다. '이너 하네스' 같은 비공식 변형은 쓰지 않습니다.

# Part 2 — 개발자가 쓰는 도구
*개발자는 **쓰던 도구**를 바꾸지 않습니다*

> **이 파트의 서술 원칙** — 도구마다 ① 누가 ② 무엇을 위해 쓰는지를 앞에 두고,
> **그 도구만의 강점**을 크게 답니다. 경쟁 도구에도 있는 기능은 하단에 작게
> `참고` 로만 두거나 뺍니다. 기능 나열은 차별점을 가립니다.

## 3-1. Copilot CLI — 터미널에서 **PR 생성**까지

전 플랜 포함 · core CLI GA

**주 사용자 — 터미널에서 대부분의 작업을 처리하는 개발자**
- CI/CD 를 많이 다루는 플랫폼 엔지니어
- SSH 로 서버에 접속해 작업하는 인프라 팀
- IDE 를 사용하지 않는 시니어 개발자

**이 도구만의 것**
- **사용하시던 셸 안에서 그대로 실행됩니다** — 에이전트 사용을 위해 환경을 변경하지 않습니다. SSH 세션과 CI 파이프라인 안에서 그대로 호출합니다.
- **파일이 많아도 고칠 자리를 정확히 찾습니다** — 코드를 훑어 짐작하지 않고 구조를 그대로 확인합니다. 오래되고 복잡한 프로젝트일수록 차이가 큽니다.

`참고 · 다른 에이전트 CLI 에도 있는 것` — MCP 연결 · custom agents · skills · hooks · plan 모드 · 클라우드 샌드박스(Preview)

**디자인 메모** · 이 슬라이드의 부제가 `전 플랜 포함` 이므로, 차별점 자리에는
**관리자 설정이나 상위 플랜이 필요 없는 것만** 둡니다. 전제가 붙는 기능을 여기 두면 부제와 모순되고,
고객이 "그건 우리도 되나" 를 되묻는 순간 슬라이드의 논지가 무너집니다.

동시에 **다른 도구가 못 하는 것**이어야 합니다. 아래 참고 칩이 `MCP 연결` 같은 공통 기능을 이미 밝히고 있어서,
그 목록과 겹치는 항목을 차별점 칸에 두면 한 화면 안에서 자기모순이 됩니다.

`LSP 언어 서버` 기능이 두 조건을 모두 만족합니다. 다만 **슬라이드에는 기술 용어를 쓰지 않습니다** —
고객이 `LSP` 가 무엇인지 되묻는 순간 이 장의 논지가 아니라 용어 설명에 시간을 쓰게 됩니다.
화면에는 이득만 적고(`고칠 자리를 정확히 찾습니다`), 구현 이름은 노트에 둡니다.

> 🎙 화면에는 안 적었지만, 이 정확도의 근거는 **LSP 언어 서버**입니다. 대부분의 에이전트 CLI 는 파일을 읽고 텍스트로 검색해 코드를 파악하는데, Copilot CLI 는 프로젝트 언어의 LSP 서버를 붙여 정의로 이동이나 심볼 참조 같은 정보를 그 언어의 컴파일러 · 분석기에서 직접 받습니다. 파일이 많고 상속과 인터페이스가 얽힌 오래된 코드베이스일수록 차이가 큽니다.
>
> 기술 청중이 "어떻게 그게 되냐" 고 물으면 그때 LSP 를 꺼내세요. 먼저 꺼내지는 마십시오.
>
> ⚠️ **언어마다 LSP 서버를 붙여야 합니다.** 설치하면 모든 언어가 자동으로 되는 것은 아니라고 정확히 말하세요.
>
> **여기 두지 않은 것들 — 물어보면 구두로**
> - *원격 제어*(터미널 세션을 `GitHub.com` · `GitHub Mobile` 에서 이어받기) — 좋은 기능이지만 조직 시트 사용자는 관리자가 `Store local sessions in the Cloud` 정책을 `View and control` 로 켜야 합니다(**기본 미설정**). 전제가 붙어서 이 자리에 두지 않았습니다.
> - *되돌리기*(`Esc` 두 번으로 세션 중 변경 롤백) — 유용하지만 **다른 에이전트 CLI 에도 비슷한 기능**이 있어 차별점으로 말하기 어렵습니다.
> - *GitHub MCP Server 내장* — 아래 참고 칩의 `MCP 연결` 과 모순됩니다.

> 🎙 이전의 `gh copilot suggest` 확장과는 다른 물건입니다. core CLI 는 GA, 클라우드 샌드박스는 public preview 입니다.
>
> ⚠️ **정확히 구분할 것** — AGENTS.md 와 `.claude/agents` 규약은 Anthropic Claude Code 에서 출발한 관례이고 GitHub 은 호환을 지원하는 쪽입니다. "AGENTS.md 는 GitHub 기능입니다" 라고 말하면 기술 청중에게 바로 신뢰를 잃습니다. GitHub 고유 지시 파일은 `copilot-instructions.md` 입니다.

## 3-2. VS Code — 자동완성은 그대로, **필요할 때만** 에이전트로

가장 많은 개발자가 이미 사용하는 환경

**주 사용자 — 편집기 안에서 대부분의 시간을 보내는 개발자**
- 가장 넓은 사용자층 — 도입 효과가 가장 먼저 나타납니다
- 에이전트를 아직 사용하지 않는 개발자까지 포함

**이 도구만의 것**
- **인라인 제안은 AI Credits 를 차감하지 않습니다** — 에이전트를 사용하지 않는 개발자에게도 도입 효과가 있습니다.
- **Session Target 에서 하네스를 바꿉니다** — Local · Copilot · Claude · Codex · Cloud. 하네스 전환이 실제로 이루어지는 지점입니다.

`참고 · 에이전트형 편집기라면 대체로 제공` — Ask 역할 · Agent 역할 · Plan 역할

> 🎙 ⚠️ **용어를 반드시 지킬 것** — VS Code 의 현재 공식 표현은 Ask · Agent · Plan **'역할(role)'** 입니다. '에디터 모드' 나 '에이전트 모드' 같은 옛 명칭은 쓰지 마세요. Edit mode 는 현재 문서에서 별도 모드로 존재하지 않습니다.
>
> **비용 대화에서 중요** — 인라인 제안은 이 세 역할과 별개이고 AI Credits 를 차감하지 않습니다.

## 3-3. Copilot app — 여러 작업을 **동시에** 진행합니다

에이전트 기반 개발 전용 데스크톱 앱 · 전 플랜 포함

**주 사용자 — 여러 작업을 동시에 진행하는 사람**
- 팀 리드 · 시니어 — 대기 시간이 곧 비용이 되는 역할
- 리팩터링 · 업그레이드처럼 오래 걸리는 작업

**이 도구만의 것**
- **작업마다 별도 브랜치 · 워크트리** — 세션끼리 서로 간섭하지 않습니다. 하나가 실행되는 동안 다른 작업을 시작하고, 진행 중인 작업을 검토할 수 있습니다.
- **이슈에서 PR 리뷰까지 앱을 벗어나지 않습니다** — CI 상태 확인과 PR 생성 · 리뷰가 같은 화면 안에 있습니다.

`참고 · 세부 기능` — Interactive · Plan · Autopilot 모드 · automations 예약 실행 · macOS · Windows · Linux

> 🎙 한 사람이 여러 작업을 동시에 진행하는 워크플로를 위한 도구입니다. 세션 모드는 위험도에 따라 고르는 것이 실무 패턴입니다.
>
> ⚠️ 공식 명칭은 **GitHub Copilot app** 입니다. 'Copilot Desktop' 이 아닙니다.

## 3-4. 도달 범위 — 팀마다 도구가 달라도 **관리는 한 곳**입니다

도구를 몇 개 쓰든 시트 · 정책 · 감사 · 비용은 GitHub 한 곳에서 봅니다.

**디자인 메모** · 허브 다이어그램. 가운데는 `GitHub 한 곳에서 관리 / 시트 · 정책 · 감사 · 비용`,
그 아래 헤어라인으로 구분해 작은 강조색 한 줄 `GitHub.com 엔터프라이즈 · 조직 설정` — 관리 지점이 실제로 어디인지 묻는 청중용 표시입니다.
좌우로 호출 지점 여섯 개. 목록으로 두면 "제품이 여섯 개"로 읽혀 이 슬라이드의 목적이 사라집니다.

> 💡 **바깥 노드는 도메인이 아니라 제품 표면 이름으로 통일합니다.**
> 다섯 개가 `GitHub Copilot CLI` · `VS Code` 처럼 제품명인데 하나만 `github.com` 이면 층위가 어긋나 보입니다.
> 웹에서 호출하는 지점은 **`GitHub Repository`** 로 적고, 도메인 표기(`GitHub.com`)는 가운데 관리 상자에만 둡니다.

> 💡 **중앙을 "같은 에이전트"로 쓰지 마십시오.** 그건 아키텍처 서술이라 기업 청중에게 편익으로 읽히지 않습니다.
> 고객이 사는 것은 **관리 지점이 하나**라는 사실입니다.

| 좌 | 우 |
|---|---|
| **GitHub Copilot CLI** — 터미널 · SSH · CI 안에서 | **GitHub Copilot app** — 브랜치별 병렬 세션 |
| **VS Code · Visual Studio** — 편집기에서 인라인 + 에이전트 | **GitHub Repository** — 이슈 할당 · PR 코멘트로 호출 |
| **JetBrains · Eclipse · Xcode · Neovim** — 팀마다 다른 IDE 그대로 | **GitHub Mobile** — 이동 중 확인과 지시 |

> **도구가 늘어도 관리 대상은 늘지 않습니다**
> 이미 쓰고 계신 GitHub 안에 있어 통제 체계를 새로 만들지 않아도 됩니다

> 🎙 개발 조직이 한 가지 도구만 쓰는 경우는 드뭅니다. 닷넷 팀은 Visual Studio, 자바 팀은 JetBrains, iOS 팀은 Xcode, 인프라 팀은 Neovim 이나 터미널을 씁니다.
>
> **플랫폼팀·구매에 가장 잘 먹히는 논리** — 보통 새 도구를 도입하면 관리 대상이 하나 늘어납니다. 시트를 따로 사고, 정책을 따로 만들고, 감사 로그가 한 곳 더 생깁니다. GitHub Copilot 은 이미 관리 중인 GitHub 안에 있어서 그 부담이 없습니다. **도달 지점이 여섯 곳이어도 관리 지점은 하나입니다.**
>
> **개발자에게는 이렇게** — 지시 파일(`copilot-instructions.md`)과 MCP 설정이 도구를 옮겨도 그대로 따라갑니다.
>
> 가운데 상자 아래 `GitHub.com 엔터프라이즈 · 조직 설정` 은 관리 지점이 실제로 어디인지 묻는 분들을 위한 표시입니다. 시트와 정책은 엔터프라이즈 · 조직 설정 화면 한 곳에서 봅니다.
>
> ⚠️ **"모든 정책이 모든 도구에 일괄 적용된다" 로 과장하지 마세요.** MCP 정책은 GitHub 호스팅 표면에 적용되고 VS Code · CLI 의 MCP 사용은 제어되지 않습니다. 감사 로그도 GitHub.com 활동이 대상이고 로컬 IDE 프롬프트는 포함되지 않습니다. 정확한 경계는 Part 4 에서 다룹니다.
>
> **반드시 나오는 질문** — "도구가 여섯 개면 설정도 여섯 벌 만들어야 하지 않냐." 아닙니다 — 자산은 그대로 이관됩니다.

# Part 3 — Agentic SDLC
*코딩만 빨라지는 게 아니라 **개발 전 과정**이 바뀝니다*

이슈 할당 · 코드 수정 · 리뷰 · 보안 검증 · 배포까지 에이전트가 수행합니다.
GitHub Copilot 과 GitHub Enterprise 를 함께 쓸 때 한 플랫폼에서 이어집니다.

## 4. 노트북을 닫아도 **에이전트는 계속 실행**합니다

Cloud Agent 가 이슈를 받아 GitHub Actions 기반 임시 환경에서 비동기로 실행합니다.

**디자인 메모** · 제목의 주어는 **에이전트**로 통일합니다. Part 3 의 §5 · §6 이 모두 "에이전트가 실행 · 처리한다" 로
이어지는데 이 장만 제목에 제품명(`Cloud Agent`)을 세우면 흐름이 끊기고, 청중에게는 **새 제품을 하나 더 소개하는 것**처럼 들립니다.
제품명은 부제에서 한 번 정확히 짚어 주는 것으로 충분합니다.

> 💡 **제품명은 부제 · 표 · 노트에서 정확하게, 제목에서는 행위 주체로.**
> 제목은 고객이 얻는 결과를 말하는 자리이고, 제품명은 그 결과를 만드는 수단입니다.

```
이슈 할당 → 조사 · 계획 → 브랜치 수정 → 보안 검증 → PR · 사람 리뷰
```

**에이전트가 만든 코드는 PR 확정 전에 CodeQL · secret scanning · 의존성 검사를 자동으로 거칩니다. 이 사전 검증에는 별도 보안 라이선스가 필요하지 않습니다.**

> 🎙 이 장에서 파는 것은 '비동기' 라는 성질 자체가 아니라 **사람이 붙어 있지 않아도 실행이 이어진다**는 결과입니다.
>
> ⚠️ **정식 명칭은 `GitHub Copilot cloud agent`** 입니다. 2026년 4월 1일자로 `coding agent` 에서 개명됐으니 예전 이름을 쓰지 마세요. 고객사 문서나 설정 화면에 아직 `coding agent` 로 남아 있을 수 있다는 점은 미리 짚어 두면 좋습니다.
>
> GitHub Enterprise Cloud 업셀의 실질적 근거입니다. 로컬 전용 에이전트는 개발자의 세션에 묶여서 노트북을 닫으면 멈춥니다. 그래서 대규모 리팩터링이나 의존성 일괄 업그레이드 같은 장시간 작업을 맡기기 어렵습니다.
>
> **반드시 나오는 반론 3가지**
> 1. *사람 없이 도는데 검증은 누가 하느냐* — PR 확정 전에 CodeQL, secret scanning, GitHub Advisory Database 기반 의존성 검사를 자동으로 거칩니다. 공식 문서는 이 security validation 에 별도 보안 라이선스가 필요하지 않다고 명시합니다.
>    ⚠️ **범위를 정확히 말하세요.** 이건 에이전트 산출물에 대한 **사전 검증**이지 리포지토리 전체에 대한 상시 code scanning 이 아닙니다. 사설 리포의 상시 스캔과 Security 탭 알림은 **GitHub Code Security · GitHub Secret Protection** 이 필요합니다. "이제 보안 제품 안 사도 된다" 로 들리게 말하면 나중에 반드시 문제가 됩니다.
> 2. *소스가 밖으로 나가느냐* — 조직의 GitHub 안에서 실행되고 방화벽·네트워크 정책이 샌드박스까지 확장 적용되며 리포지토리 단위 opt-out 도 가능합니다.
> 3. *CI 비용이 늘지 않느냐* — 에이전트 코드에 대한 CI 실행 시점을 브랜치 단위로 통제할 수 있습니다.
>
> ⚠️ 샌드박스는 public preview. '앰비언트 에이전트' 는 공식 용어가 아닙니다.

## 5. 계획부터 배포까지 **에이전트가 실행**합니다

GitHub Copilot 과 GitHub Enterprise 를 함께 쓰면 한 플랫폼에서 이어집니다.

| 구간 | GitHub 기능 | 에이전트가 실행 |
|---|---|---|
| 계획 | Issues + Planning Agent | **요구사항을 작업 단위로 분해** |
| 코딩 | Agent Mode + Cloud Agent | **브랜치 수정 · 테스트 · PR 생성** |
| 리뷰 | Copilot Code Review | **PR 1차 검토 · 수정 제안** |
| 테스트 · 보안 | Code Security + Copilot Autofix | **취약점 탐지 · 수정 PR 생성** |
| 배포 · 운영 | Actions + Agentic Workflows | **반복 작업 · 재검증 실행** |

> **실행이 사람의 대기 시간에 묶이지 않습니다**
> 다만 에이전트는 스스로 승인하거나 병합하지 않습니다 — 종착점은 언제나 Issue 또는 Draft PR 입니다

**디자인 메모** · 오른쪽 열(에이전트)이 주장이라 굵게 크게. 가운데 열(기능명)은 흐리게 — 기술 청중용 보조입니다.
사람 몫은 **밴드 아랫줄 한 줄로만** 둡니다. 별도 열이나 별도 장으로 빼면 자동화 메시지가 반감됩니다.

> 💡 **승인 게이트를 독립 슬라이드로 만들지 마십시오.** Part 3 의 세 장이 이미 각각 `PR · 담당자 검토` ·
> `Issue 또는 Draft PR` · `리뷰 · CI 검증` 으로 끝납니다. 여기에 게이트 전용 장을 더하면 같은 말이 네 번 반복되고,
> 자동화를 팔러 온 파트가 방어 설명으로 읽힙니다. 보증 문장은 이 밴드 한 줄로 충분하고, 파고드는 질문은 노트로 받습니다.

> 🎙 자동화의 대상이 코딩 한 구간이 아니라 **파이프라인 전체**이고, 그 실행을 에이전트가 맡습니다. 오른쪽 열을 위에서 아래로 읽어 주세요.
>
> 가운데 열은 "무엇으로 되느냐" 를 묻는 기술 청중용입니다. 개발 리더 중심이면 짧게 넘어가세요.
>
> 가장 큰 효과는 **대기 시간이 사라지는 것**입니다. 사람이 붙어 있어야 진행되던 구간이 사라지므로, 리팩터링이나 의존성 일괄 업그레이드처럼 미뤄 두던 작업을 실제로 돌릴 수 있게 됩니다.
>
> **도입 저항을 크게 줄이는 문장** — "프로세스를 새로 만드실 필요가 없습니다. 지금 쓰시는 리뷰 규칙과 CI 게이트가 그대로 에이전트에게도 적용됩니다."
>
> 밴드 아랫줄이 이 장의 안전장치입니다. 짧게만 언급하고 넘어가되, 통제 구조를 파고드는 분이 있으면 아래로 답하세요.
>
> **보안 · 플랫폼팀이 반드시 묻는 것**
> 1. *"에이전트가 프로덕션에 바로 나가느냐"* → 아닙니다. 자동화의 종착점은 Issue 아니면 Draft PR 이고, 병합과 운영 배포에 각각 사람 승인이 있습니다.
> 2. *"기존 required checks 가 무력화되느냐"* → 아닙니다. 에이전트가 만든 PR 도 같은 required reviews 와 required checks 를 그대로 통과해야 합니다.
> 3. *"에이전트가 push 하면 CI 가 그냥 도느냐"* → 아닙니다. 기본값은 사람이 **Approve and run workflows** 를 눌러야 실행됩니다. 시크릿에 접근하는 자동화가 사람 검토 없이 도는 것을 막기 위한 설계이고, 자동 실행 허용은 관리자가 따로 켜야 하며 공식 문서도 권장하지 않습니다.
> 4. *"환경이 오염되느냐"* → 격리된 임시 환경에서 실행됩니다.
>
> ⚠️ Copilot 의 코드 리뷰는 **required human review 를 대체하지 않습니다.** "리뷰까지 에이전트가 대신한다" 로 말하지 마세요.
>
> 이 흐름은 GitHub Actions 로 구성한 실제 데모로 시연할 수 있습니다 — 참고 구현: `github.com/hijigoo/dev-agent-workflow`
>
> ⚠️ 'Agentic DevOps' 는 GitHub 공식 브랜드 용어라는 근거가 확인되지 않았습니다. 공식 제품명처럼 말하지 마세요.

## 6. GitHub 이 찾은 문제를 **에이전트가 처리**합니다

Dependabot · CodeQL · 정기 테스트가 찾고, 할당하면 수정 PR 까지 에이전트가 만듭니다.

| 탐지 — GitHub 기능 | 무엇을 찾는가 | 에이전트에 할당하면 |
|---|---|---|
| **Dependabot** | 오래된 · 취약한 패키지 버전 | **업그레이드 수정 PR** |
| **CodeQL code scanning** | 코드 취약점 · 보안 결함 | **취약점 수정 PR** |
| **Actions 정기 테스트** | 회귀 · 실패한 E2E 시나리오 | **원인 수정 PR** |

**알림 이후** — `탐지 알림 · Issue` → `사람이 에이전트에 할당` → `에이전트가 수정 PR` → `리뷰 · CI 검증`

> **탐지 도구는 지금 쓰시는 것 그대로입니다**
> 달라지는 것은 알림 다음입니다 — 사람이 손으로 고치던 자리에 에이전트가 들어갑니다

**디자인 메모** · 제목의 주어는 **에이전트**입니다. 이 장의 판매 포인트가 "처리된다" 이기 때문입니다.
탐지 주체는 제목의 수식절(`GitHub 이 찾은`)과 부제, 그리고 표의 왼쪽 열이 함께 책임집니다 — 세 곳에서 받쳐 주므로
제목이 에이전트를 앞세워도 "에이전트가 점검까지 한다" 로 읽히지 않습니다.

**디자인 메모** · 왼쪽 열에 **제품명을 그대로** 세웁니다. 여기를 `의존성 점검` · `보안 분석` 같은 활동명으로 두면
**에이전트가 점검까지 수행하는 것으로 오해**됩니다. 탐지 주체(제품)와 해결 주체(에이전트)가 다른 열에 있어야
슬라이드 한 장으로 역할 구분이 전달됩니다.

> 🎙 이 슬라이드에서 반드시 정확히 말해야 하는 구분이 하나 있습니다. **문제를 찾는 것은 에이전트가 아닙니다.** Dependabot, CodeQL code scanning, Actions 로 돌리는 정기 테스트가 찾습니다. 전부 지금도 쓰고 계신 기능입니다.
>
> 에이전트가 들어오는 지점은 **그 다음**입니다. 예전에는 알림이 떠도 사람이 붙어야만 처리가 됐고, 그래서 백로그에 쌓였습니다. 이제 그 알림을 Issue 로 만들어 에이전트에 할당하면 수정 PR 까지 에이전트가 만들어 옵니다.
>
> **가장 잘 먹히는 문장** — "새로 도입하실 도구는 없습니다. 이미 알림은 오고 있었고, 안 고쳐지고 있었을 뿐입니다."
>
> **표 읽는 법** — 왼쪽 열은 제품명 그대로 읽고, 가운데는 그 도구가 무엇을 찾는지, 오른쪽은 할당했을 때 에이전트가 돌려주는 결과물입니다. 한 줄씩 좌→우로 읽으면 역할 구분이 자연스럽게 전달됩니다.
>
> ⚠️ **"에이전트가 보안 점검을 한다" 로 말하지 마세요.** 보안 점검은 CodeQL 이 하고 에이전트는 그 결과를 고칩니다. 보안팀이 있는 자리에서 이 구분이 흐려지면 신뢰를 잃습니다.
>
> ⚠️ 완전 무인으로 들리게 말하지 마세요. 에이전트에 할당하는 주체는 사람이고 그게 통제 지점입니다. 결과물도 리뷰와 CI 를 그대로 통과합니다.
>
> ⚠️ 탐지에서 Issue 생성까지 자동으로 잇는 부분은 **GitHub Actions 로 구성하는 운영 패턴**입니다. 제품에 내장된 버튼 하나가 아니라 조직이 자기 기준에 맞춰 만드는 워크플로라고 설명하세요. 참고 구현: `github.com/hijigoo/dev-agent-workflow`
>
> ⚠️ Dependabot 은 단순 버전 범프 PR 은 스스로 엽니다. 에이전트가 필요한 경우는 **업그레이드로 코드가 깨져서 수정이 따라와야 하는 경우**라고 덧붙이면 정확합니다.

# Part 4 — 거버넌스
*자동화를 늘릴수록 **통제권**이 더 중요해집니다*

모델 · 에이전트 · MCP · 감사 · 비용을 조직이 관리합니다.
두 장입니다 — 무엇을 켜고 끄는가, 무엇이 남고 얼마가 드는가.

## 7. 모델 · 에이전트 · MCP 까지 **중앙에서 관리**합니다

엔터프라이즈가 상한을 정하고, 그 안에서 조직이 세부를 결정합니다.

| 엔터프라이즈 — 전사 상한을 정합니다 | 무엇을 정하나 |
|---|---|
| **기능 · 클라이언트** | Chat · CLI · app · Mobile 별 사용 허용 |
| **모델** | 모델별 허용 여부와 신규 모델 기본값 |
| **공개 코드 제안** | 공개 코드와 일치하는 제안 차단 |
| **에이전트** | Cloud Agent · 서드파티 코딩 에이전트 |
| **MCP** | MCP 서버 사용 허용 |

| 조직 — 위임받은 범위 안에서 정합니다 | 무엇을 정하나 |
|---|---|
| **정책** | 엔터프라이즈가 위임한 항목을 조직이 결정 |
| **모델** | 선택 항목으로 열린 모델의 사용 여부 |
| **Cloud Agent** | 리포지토리 단위로 사용 허용 · 제외 |
| **콘텐츠 제외** | 파일 · 경로 · 리포지토리를 컨텍스트에서 제외 |
| **인터넷 접근** | Cloud Agent 방화벽과 허용 도메인 |

> **기본값이 이미 보수적으로 잡혀 있습니다**
> Cloud Agent 와 MCP 정책은 기본 비활성이고, 공개 코드 일치 제안은 Copilot Business 에서 기본 차단입니다

**디자인 메모** · 제목의 주어는 **관리 범위**이지 설정 화면이 아닙니다. 이전 제목(`설정 화면에서 정합니다`)은
UI 를 주인공으로 세워서, 값이 아닌 조작 방법이 결론처럼 읽혔습니다. 고객이 사는 것은 화면이 아니라
**모델 · 에이전트 · MCP 까지 관리 지점이 하나로 유지된다**는 사실입니다.

> 💡 3-4(`도구가 달라도 관리는 한 곳`)와 `관리` 라는 단어가 겹치는 것은 **의도한 반복**입니다.
> 2부에서는 도구가 늘어도 관리 지점이 하나, 4부에서는 AI 통제 항목이 늘어도 관리 지점이 하나 — 같은 논지를 두 번 확인시킵니다.

**디자인 메모** · **메뉴 경로(`Settings → …`)는 화면에 두지 않습니다.** 이 자리에서 필요한 답은
"어디를 클릭하느냐" 가 아니라 **"무엇을 통제할 수 있느냐"** 이고, 경로를 적어 두면 GitHub 가 화면을 개편할 때마다
슬라이드가 틀린 정보가 됩니다. 왼쪽 열은 **통제 항목**으로 두고, 경로는 발표자 노트에만 남깁니다.
두 패널의 머리를 액센트로 채워 좌우가 같은 층위(엔터프라이즈 / 조직)임을 먼저 보이게 합니다.

> 🎙 제목이 말하는 것은 화면이 아니라 **범위**입니다. 새 AI 도구를 들이면 보통 관리 대상이 하나 더 생기는데, 여기서는 모델 선택도 에이전트도 MCP 까지도 이미 쓰고 계신 GitHub 관리 체계 안에 들어옵니다. **통제 항목이 늘어나는 게 아니라 관리 지점이 그대로**라는 것이 이 장의 주장입니다.
>
> 왼쪽이 엔터프라이즈가 정하는 것, 오른쪽이 조직이 정하는 것입니다. 엔터프라이즈가 상한을 정하고, 조직은 그 상한 안에서만 움직입니다.
>
> **경로를 물어보면 — 구두로만** 엔터프라이즈는 `Settings` 안의 `AI controls` 이고 그 아래 `Copilot` · `Agents` · `MCP` 로 나뉩니다. 조직은 `Settings` 안의 `Copilot` 이며 `Policies` · `Models` · `Cloud agent` · `Content exclusion` · `Internet access` 가 있습니다. 데모 계정을 띄워 함께 보는 편이 가장 확실합니다.
> 엔터프라이즈에서 잠근 항목은 조직 소유자가 덮어쓸 수 없고, 위임하면 조직이 각자 정합니다.
>
> **가장 강한 카드는 기본값입니다** — Copilot cloud agent 는 Copilot Business · Enterprise 에서 **기본 비활성**이라 관리자가 켜야 쓸 수 있습니다. `MCP servers in Copilot` 정책도 **기본 비활성**입니다. 공개 코드와 일치하는 제안은 Copilot Business 에서 **기본 차단**입니다. "켜져 있는 걸 꺼야 하는" 구조가 아니라 **"필요한 것만 켜는"** 구조라는 점을 짚으세요.
>
> ⚠️ MCP 정책은 **서버별 허용 목록이 아니라 사용 여부 스위치**입니다. "어떤 MCP 서버는 되고 어떤 건 막는다" 는 정책 차원에서 불가능합니다.
>
> ⚠️ MCP 정책의 적용 범위는 GitHub 가 호스팅하는 GA 표면입니다. Cursor · Windsurf · Claude 같은 서드파티 호스트에서의 GitHub MCP 서버 사용은 이 정책으로 제어되지 않습니다.
>
> ⚠️ Content exclusion 은 **Copilot CLI 와 IDE 의 에이전트 모드에서는 지원되지 않습니다.** 웹사이트와 GitHub Mobile 적용은 public preview 입니다. 전면 차단 수단으로 소개하지 마세요.
>
> ⚠️ Cloud Agent 방화벽은 에이전트가 Bash 로 시작한 프로세스에 적용되고 **MCP 서버에는 적용되지 않습니다.** 만능 보안 장치로 말하지 마세요.
>
> ⚠️ 화면 구성은 GitHub 가 개편할 수 있습니다. 고객사 화면과 다르면 그 자리에서 함께 확인하겠다고 답하는 편이 안전합니다.

## 8. 누가 무엇을 했는지 남고, **비용은 상한 안에서** 돕니다

정책으로 범위를 정했다면, 남는 것은 기록과 사용량 관리입니다.

| # | 항목 | 내용 |
|---|---|---|
| 01 | 정책 우선순위 | 엔터프라이즈가 잠그면 조직이 덮어쓸 수 없고, 위임하면 조직이 정합니다 |
| 02 | 감사 | 에이전트 활동이 `actor:Copilot` 로 검색되는 전용 이벤트로 남고 180일 보존됩니다 |
| 03 | 크레딧 | AI Credits 는 청구 단위로 풀링되어 조직이 하나의 풀을 공유합니다 |
| 04 | 예산 상한 | 엔터프라이즈 · 조직 · 코스트센터 · 사용자 단위로 한도를 겁니다 |

> **전 직원에게 배포해도 비용은 에이전트를 쓴 만큼만 늘어납니다**
> 코드 자동완성과 다음 편집 제안은 유료 플랜에서 무제한이고 크레딧을 쓰지 않습니다 — 크레딧은 Chat · CLI · Cloud Agent 실행에만 소비됩니다

**디자인 메모** · 이전 밴드는 `코드 자동완성은 AI Credits 를 소비하지 않습니다` 라는 **메커니즘**만 말했고,
그게 무슨 뜻인지는 청중이 스스로 계산해야 했습니다. 밴드는 슬라이드의 결론 자리이므로 **함의를 먼저** 말합니다 —
배포 인원(고정비)과 에이전트 사용량(변동비)을 **분리해서 결정할 수 있다**는 것이 이 장의 결론입니다.
`actor:Copilot` 은 밴드에서 빼고 02 카드로 옮겼습니다. 밴드에 비용과 감사를 같이 담으면 결론이 둘이 됩니다.

> 🎙 앞 슬라이드가 "무엇을 켜고 끄느냐" 였다면 이 장은 **"그 다음에 무엇이 남고 얼마가 드느냐"** 입니다.
>
> **01 정책 우선순위** — 엔터프라이즈에서 전체 비활성으로 잠그면 조직 소유자가 덮어쓸 수 없습니다. `No policy` 로 두면 조직별로 정합니다. 지주회사 · 계열사 구조 고객에게 특히 중요합니다.
>
> **02 감사** — `actor:Copilot` 으로 검색하고 보존 기간은 180일입니다.
> ⚠️ **로컬 IDE 에서 보낸 프롬프트는 감사 로그에 포함되지 않습니다.** 먼저 밝히고 들어가는 편이 신뢰를 얻습니다.
> ⚠️ 사용량 레코드 스트리밍은 **public preview** 이고 EMU 또는 데이터 레지던시 환경에 한정됩니다. GA 로 말하지 마세요.
>
> **03 크레딧** — billing entity 단위로 풀링됩니다. 시트마다 개별 할당이 아니라 조직이 하나의 풀을 공유하고, 미사용분은 이월되지 않습니다.
>
> **04 예산 상한** — 한도를 걸지 않으면 초과분은 계속 과금되므로 관리자가 명시적으로 설정해야 한다고 안내하세요.
>
> **밴드가 이 장의 실질적 결론입니다** — *"전 직원에게 깔면 비용이 폭증하지 않느냐"* 가 이 파트에서 가장 자주 나오는 질문이고, 답이 밴드에 있습니다. **배포 인원과 변동비를 분리해서 결정하실 수 있다**는 뜻입니다.
> 공식 문서 표현 그대로 — *"Code completions and next edit suggestions are not billed in AI credits. They remain unlimited for all paid plans."*
>
> **이어서 제안할 실행안** — 파일럿 조직이나 코스트센터 하나에 예산 상한을 걸고 시작하십시오. 한 달 뒤 감사 기록과 크레딧 사용량을 함께 보면 확대 범위를 **예측이 아니라 실측으로** 정할 수 있습니다.
>
> ⚠️ 이 자리에서 단가나 크레딧 수량을 먼저 꺼내지 마세요. 구조(**시트 = 고정비, 크레딧 = 변동비**)만 설명하고 금액은 범위를 합의한 뒤 견적으로 드립니다.
>
> ⚠️ 그 자리에서 단정하지 말 것 — IP 배상의 구체적 범위, 데이터 레지던시. 법무 · 약관 확인 후 회신한다고 답하세요.
> ⚠️ 용어는 `AI controls` 를 쓰고 `Agent HQ` 는 문서에 없는 표현이라 관리자 문맥에서 쓰지 않습니다.

# Part 5 — 도입 프로그램
*도구 도입이 아니라 **Agentic 개발 문화**를 함께 만듭니다*

1시간 브리핑부터 2개월 정착 프로그램까지

## 9. 목적에 따라 **네 가지 프로그램**을 제안드립니다

**용어 메모** · 파트 이름은 `인에이블먼트` 가 아니라 **`도입 프로그램`** 입니다.
`인에이블먼트` 는 우리 쪽 업무 용어라 고객 화면에서는 무엇을 받는지가 드러나지 않습니다.

**디자인 메모** · 제목은 **제안**이지 요구가 아닙니다. `기간을 고르십니다` 는 고객에게 숙제를 넘기는 말이고,
이 장은 우리가 준비해 둔 것을 펼쳐 보이는 자리입니다.
바로 다음 장(`어느 단계에 계시든 맞는 과정이 준비되어 있습니다`)과 역할도 갈라집니다 —
**여기는 무엇이 있는지(카탈로그), 다음 장은 어느 것부터 시작하는지(연결)** 입니다.

한 시간짜리 브리핑부터 두 달짜리 정착 프로그램까지.

| 기간 | 과정 | 대상 | 무엇을 하는가 |
|---|---|---|---|
| **1시간** | **경영진 브리핑** | C-Level · 개발 임원 | AI 개발 도입이 어느 프로세스를 바꾸는지 정리하고 투자 우선순위를 맞춥니다 |

## 10. 어느 단계에 계시든 **맞는 과정이 준비**되어 있습니다

조직마다 출발점이 다릅니다. 상황별로 시작 지점과 다음 단계를 미리 정리해 두었습니다.

**디자인 메모** · 이전 제목(`현재 상태를 말씀해 주시면 시작점이 정해집니다`)은 **고객이 먼저 답해야 다음이 열리는** 구조라
오퍼링 자리에서 심사받는 느낌을 줬습니다. 제목은 요구가 아니라 **제안**이어야 합니다.
같은 표를 두고도 "말씀해 주시면 정해 드리겠다" 와 "어느 쪽이시든 이미 준비해 두었다" 는 완전히 다르게 들립니다.

|---|---|---|

| 시트는 도입했으나 개발팀만 활용 중 | **1일** 비개발 직군 핸즈온 | 전사 확산 계획 수립 |

> **기간별로 약속 가능한 것** — 한 번의 과정으로 약속할 수 있는 것은 *기준선 · 챔피언 명단 · 다음 단계 합의*까지입니다. 사용 품질이나 사업 성과는 하루로 약속하지 마세요. "생산성 55% 향상" 같은 단일 수치는 절대 단정하지 않습니다. 고객사 파일럿에서 합의된 기준선 대비 개선폭을 측정하겠다고 말하세요.

## 부록 — 덱 디자인 규칙

**숫자로 덱을 늙히지 마십시오.** 벤더 수 · 모델명 · 단가 · 시트 수처럼 갱신 주기가 짧은 값은
슬라이드에 고정하지 않습니다. "다섯 벤더" 는 벤더가 하나 늘거나 빠지는 순간 틀린 말이 됩니다.
"여러 벤더" 로 쓰고, 정확한 목록이 필요하면 그 자리에서 공식 문서를 띄웁니다.
나열은 `등` 을 붙여 예시임을 명시합니다.

**회색은 "비활성"으로 읽힙니다.** 항목이 서로 동등하면 절대 일부만 회색으로 두지 마십시오.

| 상황 | 처리 |
|---|---|
| 네 항목이 **모두 동등** (아젠다 · 거버넌스 · 프로그램 기간) | 전부 액센트. 일부만 파랗게 하면 나머지가 폐기된 기능처럼 보입니다 |
| 순서 안에서 **역할이 다름** (실행 흐름의 중간 단계) | 회색 대신 **액센트 틴트**. "자동으로 수행되는 구간"이라는 뜻이 됩니다 |
| 자동 실행되는 **긍정적 역량** (CodeQL · secret scanning 등) | 액센트 틴트. 회색은 기능이 꺼져 있는 것처럼 보입니다 |
| **의도적 비강조** (`참고 · 다른 도구에도 있는 것`) | 회색 유지. `참고` 라벨이 의도를 명시하므로 오해 소지가 없습니다 |
| 허브 다이어그램의 주변 노드 | 회색 유지. 중앙을 강조하는 게 목적이라 주변까지 파랗게 하면 요점이 흐려집니다 |

> 액센트는 여전히 절제해야 합니다. 위 규칙은 "더 칠하라"가 아니라 **"동등한 것을 차등해 보이게 만들지 말라"** 는 뜻입니다.

### 줄바꿈 — 마지막 줄에 한두 음절만 남기지 않습니다

한글은 하이픈 분리가 없어서, 좁은 칼럼에 문장을 넣으면 끝의 한두 음절이 혼자 다음 줄로 떨어집니다.
`않습니다` · `지점입니다.` 처럼 조각만 남은 줄은 덱 전체를 급조한 것처럼 보이게 만듭니다.

**해결은 CSS 로 합니다. 손으로 `<br>` 을 넣지 마십시오** — 문구를 한 번만 고쳐도 다시 깨집니다.

```css
.slide p,.slide li,.slide h2,.slide h4,
.stat,.claim,.tag,.node span,.crow span,
.change .from,.change .aside,.change .to,
.band,.band .muted,.attrib{ text-wrap:balance; }

.nb{white-space:nowrap;}   /* "SSH 세션" 같은 라틴+한글 복합어 보호 */
```

- `text-wrap:balance` 는 줄 길이를 고르게 나눠 고아 줄을 없애고, 한 줄에 들어가는 문장은 건드리지 않습니다.
- 라틴+한글 복합어(`SSH 세션` · `CI 파이프라인`)는 사이 공백이 줄바꿈 지점이 되어 라틴 쪽만 앞줄 끝에 남습니다. `.nb` 로 감쌉니다.
- 검증은 `verify_deck.js` 가 자동으로 합니다 — 마지막 줄 길이가 가장 긴 줄의 **34% 미만**이면 `ORPHAN_LINE` 으로 실패시킵니다.
  이 규칙을 넣기 전 원고에서 6개 슬라이드가 걸렸습니다.

## 부록 — HTML 과 PPTX 를 같아 보이게 맞추기

두 형식이 미묘하게 어긋나는 원인은 대부분 셋 중 하나입니다.

**1. 본문은 세로 가운데 정렬입니다.** CSS 의 `.body` 가 `flex:1; justify-content:center` 이므로
내용 블록은 상단 룰과 하단 여백 사이에서 **중앙에 놓입니다**. 고정 `y` 로 그리면 슬라이드마다 조금씩 어긋납니다.
PPTX 생성기는 그린 객체들의 실제 상·하단을 재서 같은 규칙으로 이동시킵니다(`centreBody`).

**2. 폰트 폭이 다릅니다.** 실측값(100px 기준):

| | 한글 | 대문자 | 소문자 | 숫자 | 공백 |
|---|---|---|---|---|---|
| `IBM Plex Sans KR` (웹) | **0.892** | 0.611 | 0.422 | 0.50 | 0.356 |
| `맑은 고딕` (PPTX) | **1.00** | 0.611 | 0.422 | 0.50 | 0.356 |

한글이 **약 12% 넓습니다.** 웹에서 한 줄에 딱 맞는 제목이 PPTX 에서는 넘칠 수 있고,
이때는 줄바꿈 대신 **한 단계 축소**합니다 — 살짝 작은 제목은 의도로 보이지만, 두 줄이 겹치면 파일이 깨져 보입니다.
웹폰트를 청중의 Office 에 배포할 수 없으므로 이 차이는 없앨 수 없고, 관리만 가능합니다.

**3. 상단 크롬은 실측 좌표로 맞춥니다.** `.chrome` 이 `gap:34px` 인 flex 라 페이지 번호가
마커 바로 옆에 붙습니다. 넓은 오른쪽 정렬 상자를 쓰면 그 사이가 벌어집니다.
측정값 — 마커 `32px`, 마커 간격 `8px`, 크롬 간격 `34px`, 페이지 번호 폭 `96px`, 전체 `322px`.

> 💡 표지 `--h1-size` 는 **142px** 입니다. 168px 은 지면을 꽉 채워 소리치는 인상이었고,
> 맑은 고딕에서 한 줄에 들어가는 최대 크기이기도 해서 **두 형식이 같은 숫자를 쓸 수 있는 지점**입니다.
