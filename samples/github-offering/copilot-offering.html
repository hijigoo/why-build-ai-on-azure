[3-4. 도달 범위 — 관리는 한 곳] 개발 조직이 한 가지 도구만 쓰는 경우는 드뭅니다. 닷넷 팀은 Visual Studio, 자바 팀은 JetBrains, iOS 팀은 Xcode, 인프라 팀은 Neovim 이나 터미널을 씁니다. [플랫폼팀·구매에 가장 잘 먹히는 논리] 보통 새 도구를 도입하면 관리 대상이 하나 늘어납니다. 시트를 따로 사고, 정책을 따로 만들고, 감사 로그가 한 곳 더 생깁니다. GitHub Copilot 은 이미 관리 중인 GitHub 안에 있어서 그 부담이 없습니다. 도달 지점이 여섯 곳이어도 관리 지점은 하나입니다. [개발자에게는 이렇게] 지시 파일(copilot-instructions.md)과 MCP 설정이 도구를 옮겨도 그대로 따라갑니다. 도구마다 설정을 새로 만들 필요가 없습니다. ⚠️ "모든 정책이 모든 도구에 일괄 적용된다" 로 과장하지 마세요. 예를 들어 MCP 정책은 GitHub 호스팅 표면에 적용되고 VS Code · CLI 의 MCP 사용은 이 정책으로 제어되지 않습니다. 감사 로그도 GitHub.com 활동이 대상이고 로컬 IDE 프롬프트는 포함되지 않습니다. 정확한 경계는 Part 4 에서 다룹니다. 가운데 상자 아래 'GitHub.com 엔터프라이즈 · 조직 설정' 은 관리 지점이 실제로 어디인지 묻는 분들을 위한 표시입니다. 시트와 정책은 엔터프라이즈 · 조직 설정 화면 한 곳에서 봅니다. [반드시 나오는 질문] "도구가 여섯 개면 설정도 여섯 벌 만들어야 하지 않냐." 아닙니다 — 자산은 그대로 이관됩니다(앞 하네스 슬라이드 참조).

[4. 비동기 실행 — Cloud Agent] 제목의 주어는 '에이전트' 로 통일했습니다. Part 3 의 다음 장들이 모두 "에이전트가 실행한다" 로 이어지는데 이 장만 제품명을 제목에 세우면 흐름이 끊기고, 청중에게는 새 제품 하나를 더 소개하는 것처럼 들립니다. 제품명 Cloud Agent 는 부제에서 한 번 정확히 짚어 줍니다. 이 장에서 파는 것은 '비동기' 라는 성질 자체가 아니라, 사람이 붙어 있지 않아도 실행이 이어진다는 결과입니다. ⚠️ 정식 명칭은 GitHub Copilot cloud agent 입니다. 2026년 4월 1일자로 coding agent 에서 개명됐으니 예전 이름을 쓰지 마세요. 고객사 문서나 설정 화면에 coding agent 로 남아 있을 수 있다는 점은 미리 언급해 두면 좋습니다. GitHub Enterprise Cloud 업셀의 실질적 근거입니다. 로컬 전용 에이전트는 개발자의 세션에 묶여서 노트북을 닫으면 멈춥니다. 그래서 대규모 리팩터링이나 의존성 일괄 업그레이드 같은 장시간 작업을 맡기기 어렵습니다. [반드시 나오는 반론 3가지] 1. 사람 없이 도는데 검증은 누가 하느냐 — PR 확정 전에 CodeQL, secret scanning, GitHub Advisory Database 기반 의존성 검사를 자동으로 거칩니다. 공식 문서는 이 security validation 에 별도 보안 라이선스가 필요하지 않다고 명시합니다. ⚠️ 범위를 정확히 말하세요. 이건 에이전트 산출물에 대한 사전 검증이지 리포지토리 전체에 대한 상시 code scanning 이 아닙니다. 사설 리포의 상시 스캔과 Security 탭 알림은 GitHub Code Security · GitHub Secret Protection 이 필요합니다. "이제 보안 제품 안 사도 된다" 로 들리게 말하면 나중에 반드시 문제가 됩니다. 2. 소스가 밖으로 나가느냐 — 조직의 GitHub 안에서 실행되고 방화벽·네트워크 정책이 샌드박스까지 확장 적용되며 리포지토리 단위 opt-out 도 가능합니다. 3. CI 비용이 늘지 않느냐 — 에이전트 코드에 대한 CI 실행 시점을 브랜치 단위로 통제할 수 있습니다. ⚠️ 샌드박스는 public preview. '앰비언트 에이전트' 는 공식 용어가 아니니 Copilot cloud agent 로 부르세요.

[Agentic SDLC — 전 구간 실행] 이 슬라이드의 메시지는 하나입니다 — 자동화의 대상이 코딩 한 구간이 아니라 파이프라인 전체이고, 그 실행을 에이전트가 맡습니다. 오른쪽 열을 위에서 아래로 읽어 주세요. 다섯 구간 모두 에이전트가 실행합니다. 가운데 열(GitHub 기능)은 "무엇으로 되느냐" 를 묻는 기술 청중용입니다. 개발 리더 중심이면 짧게 넘어가세요. 가장 큰 효과는 대기 시간이 사라지는 것입니다. 사람이 붙어 있어야 진행되던 구간이 사라지므로, 리팩터링이나 의존성 일괄 업그레이드처럼 미뤄 두던 작업을 실제로 돌릴 수 있게 됩니다. [도입 저항을 크게 줄이는 문장] "프로세스를 새로 만드실 필요가 없습니다. 지금 쓰시는 리뷰 규칙과 CI 게이트가 그대로 에이전트에게도 적용됩니다." 밴드 아랫줄은 짧게만 언급하세요. 승인 권한이 사람에게 남는 건 당연한 전제이고 이 슬라이드의 주장이 아닙니다. 통제 구조를 파고드는 분이 있으면 아래로 답하세요. [보안 · 플랫폼팀이 반드시 묻는 것] 1. "에이전트가 프로덕션에 바로 나가느냐" — 아닙니다. 자동화의 종착점은 Issue 아니면 Draft PR 이고, 병합과 운영 배포에 각각 사람 승인이 있습니다. 2. "기존 required checks 가 무력화되느냐" — 아닙니다. 에이전트가 만든 PR 도 같은 required reviews 와 required checks 를 그대로 통과해야 합니다. 3. "에이전트가 push 하면 CI 가 그냥 도느냐" — 아닙니다. 기본값은 사람이 Approve and run workflows 를 눌러야 실행됩니다. 자동 실행 허용은 관리자가 따로 켜야 하고 공식 문서도 권장하지 않습니다. 4. "환경이 오염되느냐" — 격리된 임시 환경에서 실행됩니다. ⚠️ Copilot 의 코드 리뷰는 required human review 를 대체하지 않습니다. ⚠️ 'Agentic DevOps' 는 우리 오퍼링에서 범위를 가리키는 명칭으로 쓰지만, GitHub 공식 제품 문서에서 브랜드 용어로 쓰인다는 근거는 확인되지 않았습니다. 고객 앞에서 공식 제품명처럼 말하지 마세요.

[거버넌스 — 중앙 관리 범위] 제목이 말하는 것은 화면이 아니라 범위입니다. 새 AI 도구를 들이면 보통 관리 대상이 하나 더 생기는데, 여기서는 모델 선택도 에이전트도 MCP 까지도 이미 쓰고 계신 GitHub 관리 체계 안에 들어옵니다. 통제 항목이 늘어나는 게 아니라 관리 지점이 그대로라는 것이 이 장의 주장입니다. 플랫폼팀과 보안팀이 가장 먼저 확인하고 싶어 하는 것은 "우리가 무엇을 잠글 수 있느냐" 입니다. 왼쪽이 엔터프라이즈가 정하는 것, 오른쪽이 조직이 정하는 것입니다. 메뉴 경로는 화면에 두지 않았습니다. 이 자리에서 필요한 답은 "어디를 클릭하느냐" 가 아니라 "무엇을 통제할 수 있느냐" 이고, 경로를 적어 두면 GitHub 가 화면을 개편할 때마다 틀린 정보가 됩니다.
