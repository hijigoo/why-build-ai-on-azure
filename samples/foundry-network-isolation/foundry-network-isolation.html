이 문서는 Microsoft Foundry를 사설 네트워크 안에서 운영하려는 조직을 위한 자료입니다. 규제 산업이나 내부 보안 기준이 엄격한 환경에서 Foundry를 도입할 때 무엇을 결정해야 하고, 어떤 제약이 있는지를 순서대로 정리했습니다.

세 파트로 읽으면 됩니다. 먼저 인바운드(들어오는 접근을 어떻게 막을 것인가), 다음 아웃바운드(에이전트가 나가는 경로를 어떻게 통제할 것인가), 마지막으로 도구와 제약(실제로 무엇이 동작하는가)입니다.

내용은 Microsoft Learn 공식 문서를 기준으로 작성했으며 2026년 8월에 확인했습니다. 네트워크 격리 영역은 변화가 빠르므로, 도입 시점에 지원 리전과 기능 상태를 다시 확인해야 합니다.

시작하기02 / 19
슬라이드 설명

네트워크 격리는 네트워크를 여러 구간으로 나누고 각 구간을 독립된 작은 네트워크처럼 다루는 보안 전략입니다. 규제 산업의 기업은 데이터와 모델이 무단 접근·변조·유출되지 않도록 이 구조를 요구합니다.

AI 워크로드에서 특히 중요한 이유 — 에이전트는 사내 데이터를 읽는 경로와 외부로 나가는 경로를 동시에 가집니다. 인바운드만 막고 아웃바운드를 열어 두면, 데이터가 나가는 문은 그대로 열려 있는 셈입니다. 세 방향을 함께 설계해야 하는 이유입니다.

  • 인바운드 — 공용 네트워크 접근(PNA) 플래그로 정책을 정합니다. 완전 차단, 지정한 IP만 허용, 공개 중에서 고릅니다.
  • 리소스 아웃바운드 — 저장소·Key Vault·컨테이너 레지스트리·모니터링 같은 PaaS 의존 리소스를 Private Link로 격리합니다.
  • 에이전트 아웃바운드 — 학습이나 엔드포인트용 IaaS 컴퓨트를 고객이 관리하지 않습니다. 대신 플랫폼이 컨테이너 주입으로 고객 가상 네트워크에 통합합니다.
Private Link · 프라이빗 엔드포인트
Azure 서비스에 공용 인터넷을 거치지 않고 가상 네트워크 내부의 사설 IP로 접근하게 해 주는 기능입니다.
가상 네트워크 주입(VNet Injection)
플랫폼이 관리하는 컴퓨트를 고객 소유 서브넷 안에 배치하는 방식입니다. 트래픽이 고객 네트워크 경계를 벗어나지 않습니다.

공용 네트워크 접근 세 가지 선택

인바운드 격리 #
인바운드 정책

공용 접근을 어디까지 열 것인가

설정동작쓰는 경우
Disabled프라이빗 엔드포인트로만 접근 가장 강한 격리규제 대응의 기본값
Selected networks지정한 IP 주소·가상 네트워크만 허용 사무실 IP 등 제한적 공개가 필요할 때
Enabled공용 엔드포인트 개방 개발·평가 환경
두 설정은 독립적입니다 — 프라이빗 엔드포인트를 제거해도 리소스가 공개되지 않고, 공용 접근을 켜도 기존 프라이빗 엔드포인트는 그대로 유지됩니다.
Part 1 · 인바운드04 / 19
슬라이드 설명

공용 네트워크 접근(Public Network Access, PNA) 플래그가 프로젝트에 프라이빗 엔드포인트가 필요한지를 결정합니다. 공개와 완전 차단 사이의 중간 선택지가 Selected networks이며, 지정한 IP 주소에서의 접근을 허용합니다.

자주 오해하는 부분 — 프라이빗 엔드포인트를 모두 제거해도 프로젝트가 공개 상태가 되지는 않습니다. 공개하려면 방화벽 설정에서 명시적으로 모든 네트워크를 허용해야 합니다. 반대로 공용 접근을 켜더라도 프라이빗 엔드포인트를 통한 통신은 계속 보호됩니다. 공개는 프라이빗 접근에 추가되는 것이지 대체하는 것이 아닙니다.

공용 접근을 제한한 상태에서도 일부 Azure 서비스에는 예외를 둘 수 있습니다. Foundry Tools(Microsoft.CognitiveServices), Azure AI Search(Microsoft.Search), Azure Machine Learning(Microsoft.MachineLearningServices)이 해당하며, 각 서비스의 관리 ID에 적절한 역할이 부여되어 있어야 합니다.

공용 네트워크 접근(PNA)
리소스를 인터넷에서 직접 접근할 수 있게 할지 정하는 설정입니다. 끄면 사설 경로로만 접근할 수 있습니다.
관리 ID(Managed Identity)
서비스가 비밀번호나 키 없이 다른 Azure 리소스에 인증하기 위해 사용하는 자동 관리 신원입니다.

Part 1 · 인바운드05 / 19
슬라이드 설명

새 Foundry 리소스를 만들 때는 Networking 탭에서 공용 접근을 Disabled로 두고 프라이빗 엔드포인트를 추가합니다. 기존 리소스에 나중에 붙이려면 리소스의 Resource Management → Networking → Private endpoint connections에서 추가합니다.

리전을 맞춰야 합니다 — 프라이빗 엔드포인트는 가상 네트워크와 같은 리전, 같은 구독에 배포해야 합니다. 엔드포인트를 만들 때 Basics 단계에서 가상 네트워크와 동일한 리전을 선택하세요.

승인 상태를 확인하세요 — 트래픽은 Approved 상태의 엔드포인트로만 흐릅니다. 승인 권한이 없으면 연결이 Pending에 머무르므로, 리소스 소유자에게 승인을 요청해야 합니다. 엔드포인트 생성 자체가 실패한다면 가상 네트워크와 서브넷에 대한 Network Contributor 권한과 서브넷의 여유 IP를 확인합니다.

Pending / Approved 상태
프라이빗 엔드포인트 연결은 요청과 승인의 두 단계를 거칩니다. 승인 전에는 연결이 만들어져도 트래픽이 흐르지 않습니다.

가장 자주 발생하는 문제 — 사내 DNS 서버를 쓴다면 privatelink 하위 도메인을 프라이빗 DNS 영역으로 위임해야 합니다. 이 설정을 빠뜨리면 이름이 공용 IP로 풀려 연결이 실패합니다.
Part 1 · 인바운드06 / 19
슬라이드 설명

프라이빗 엔드포인트를 만들면 Azure가 Foundry 리소스의 CNAME 레코드를 privatelink 접두사가 붙은 하위 도메인의 별칭으로 갱신하고, 그에 대응하는 프라이빗 DNS 영역을 자동으로 만듭니다. 이 영역에 프라이빗 엔드포인트의 A 레코드가 등록됩니다.

이 구조의 장점 — 가상 네트워크 안팎의 클라이언트가 같은 연결 문자열을 쓸 수 있습니다. 애플리케이션 코드를 바꾸지 않아도 위치에 따라 알맞은 경로로 연결됩니다.

사내 DNS를 쓸 때 — 클라이언트가 Foundry 엔드포인트의 FQDN을 프라이빗 엔드포인트 IP로 해석할 수 있어야 합니다. DNS 서버에서 privatelink 하위 도메인을 가상 네트워크의 프라이빗 DNS 영역으로 위임하거나, 직접 A 레코드를 추가합니다. 커스텀 DNS 서버가 해석하지 못한다면 privatelink 하위 도메인 쿼리를 Azure DNS(168.63.129.16)로 전달하는지 확인하세요.

간헐적으로 실패한다면 DNS 서버가 모든 서브넷에서 도달 가능한지, 가상 네트워크와 개별 NIC의 DNS 설정이 일관된지 점검합니다.

FQDN
전체 주소 도메인 이름. 호스트와 도메인을 모두 포함한 완전한 주소입니다.
CNAME · A 레코드
CNAME은 이름을 다른 이름으로 연결하는 별칭이고, A 레코드는 이름을 실제 IP 주소로 연결합니다.

Part 1 · 인바운드07 / 19
슬라이드 설명

공용 접근을 끄면 개발자와 데이터 과학자도 가상 네트워크 안에서 접근해야 합니다. 세 가지 방법 중 조직의 기존 네트워크 구성에 맞는 것을 고릅니다. 이미 ExpressRoute나 사이트 간 VPN이 있다면 그대로 활용하면 되고, 없다면 Azure Bastion과 점프박스 VM 조합이 가장 빠릅니다.

검증 순서

  • 1단계 — 포털의 Networking → Private endpoint connections에서 상태가 Approved인지 확인합니다.
  • 2단계 — 가상 네트워크에 연결된 VM에서 nslookup <foundry-endpoint-hostname>을 실행해 프라이빗 엔드포인트의 사설 IP가 반환되는지 봅니다. 공용 IP가 나오면 DNS 구성 문제입니다.
  • 3단계 — Test-NetConnection <private-endpoint-ip> -Port 443으로 실제 연결을 확인합니다.

온프레미스에서 VPN이나 ExpressRoute를 통해 접속하는 경우에도 같은 방법으로 검증할 수 있습니다.

지점 간(P2S) · 사이트 간(S2S)
P2S는 개별 PC에 VPN 클라이언트를 설치해 연결하고, S2S는 VPN 장비로 사무실 네트워크 전체를 연결합니다.
Azure Bastion
공용 IP를 VM에 부여하지 않고 브라우저에서 RDP·SSH로 접속하게 해 주는 서비스입니다.

어느 쪽을 고를 것인가 — 판단 기준은 대체로 세 가지입니다.

  • 기존 네트워크 표준이 있다면 BYO — 허브-스포크 구조와 중앙 방화벽을 이미 운영하는 조직이라면, Foundry도 같은 표준에 편입하는 편이 관리하기 쉽습니다.

관리형 프라이빗 엔드포인트의 특징 — 표준 프라이빗 엔드포인트와 달리 고객 구독에 네트워크 인터페이스(NIC)를 만들지 않습니다. 서브넷에 사설 IP를 가진 NIC가 보이지 않으며, Microsoft가 전적으로 관리합니다. 문서의 구성도는 논리적 연결만 나타냅니다.

다음 두 장에서 각 방식을 자세히 봅니다.

BYO(Bring Your Own)
고객이 소유하고 관리하는 리소스를 가져다 쓰는 방식입니다. 데이터와 네트워크가 고객 테넌트 안에 남습니다.
NIC(네트워크 인터페이스)
가상 머신이나 엔드포인트가 네트워크에 연결되는 지점입니다. 사설 IP가 여기에 할당됩니다.

슬라이드 설명

관리형 가상 네트워크를 켜면 Microsoft 테넌트에 가상 네트워크가 만들어지고, 프로젝트에서 만든 에이전트는 자동으로 이 네트워크를 통해 아웃바운드 통신을 합니다. Azure Storage, Azure Cosmos DB, Azure AI Search 같은 의존 리소스에는 관리형 프라이빗 엔드포인트로 연결합니다.

승인된 아웃바운드 모드의 비용 — 이 모드에서 FQDN 규칙을 만들면 관리형 Azure Firewall이 자동으로 생성되며 방화벽 비용이 발생합니다. FQDN 규칙은 80·443 포트만 지원합니다. 자체 Azure Firewall을 반입할 수 없고, Foundry 계정마다 별도의 관리형 방화벽이 만들어지므로 여러 계정이 하나의 방화벽을 공유할 수 없습니다.

모드 전환이 막혀 있는 이유를 실무적으로 해석하면, 처음부터 더 엄격한 쪽으로 시작하는 편이 안전하다는 뜻입니다. 인터넷 아웃바운드로 열어 두고 나중에 조이려 해도 방법이 없습니다.

온프레미스 리소스에 사설로 접근해야 한다면 Application Gateway를 사용합니다. 프라이빗 엔드포인트를 Application Gateway에 두고 백엔드 풀을 구성하는 방식이며, L4와 L7 트래픽 모두 정식 출시 상태로 지원됩니다.

FQDN 규칙
도메인 이름 단위로 아웃바운드를 허용하는 방화벽 규칙입니다.

네트워크를 격리하면 에이전트가 쓸 수 있는 도구가 제한됩니다. 파일럿을 설계할 때 이 제약을 먼저 확인하지 않으면, 구현 단계에서 핵심 기능을 못 쓴다는 사실을 뒤늦게 발견하게 됩니다.

여기서 다루는 지원 현황은 새 Foundry 포털이나 SDK·CLI로 만든 Responses API 기반 에이전트를 기준으로 합니다. 클래식 Foundry 포털에서 만든 에이전트에는 적용되지 않습니다.

슬라이드 설명

공용 엔드포인트 도구를 주의해야 하는 이유 — Bing Grounding, Websearch, SharePoint Grounding은 격리 환경에서도 동작하지만 공용 인터넷을 경유합니다. 모든 트래픽이 사설 네트워크에 머물러야 하는 조직이라면 요건을 충족하지 못합니다. 필요하다면 Azure Policy로 이 도구들의 사용을 차단할 수 있습니다.

부분 지원 도구의 실제 동작

  • Code Interpreter — Microsoft 백본으로 통신하며 파일 없이는 정상 동작합니다. 파일 업로드·다운로드는 지원되지 않으며, SDK로 필요한 파일을 담은 컨테이너를 만들고 container_id를 전달하는 우회 방법이 있습니다. 이 방법은 Foundry 포털 UI에서는 쓸 수 없습니다.
  • Fabric IQ — MCP를 경유하며 Fabric 항목 유형별로 지원이 다릅니다. 데이터 에이전트는 테넌트 수준과 작업 영역 수준 프라이빗 링크를 지원하고, 온톨로지는 테넌트 수준만, Power BI 시맨틱 모델은 공용 접근만 지원합니다.
  • Foundry IQ — MCP를 경유해 지원됩니다.

지원 현황은 Standard 설정 템플릿과 Basic 설정 템플릿 양쪽에 적용됩니다. 격리 환경에서 도구를 구성하는 방법은 foundry-samples 저장소의 에이전트 도구 템플릿에 예제가 있습니다.

MCP(Model Context Protocol)
에이전트가 외부 도구·데이터에 접근하기 위한 표준 프로토콜입니다.
Agent-to-Agent(A2A)
에이전트끼리 서로를 호출해 협업하는 방식입니다.

이 장을 따로 둔 이유는 진단이 어려운 실패이기 때문입니다. 연결 오류나 권한 오류처럼 명확한 메시지가 뜨지 않고, 인덱싱이 성공한 것처럼 보이는데 색인만 비어 있습니다. 격리 환경에서 Azure AI Search를 쓸 때 미리 알아 두면 시간을 크게 아낄 수 있습니다.

언제 발생하나 — 인덱서가 데이터 원본을 읽으려면 그 리소스에 도달해야 합니다. 기본값인 멀티테넌트 실행 환경은 공유 인프라에서 동작하므로 고객 가상 네트워크의 프라이빗 엔드포인트를 통과할 수 없습니다. 포털의 데이터 가져오기 마법사로 만든 인덱서가 대표적인 사례입니다.

예외가 있습니다 — 인덱싱된 지식 소스와 그에 딸려 자동 생성되는 인덱서는 프라이빗 실행 환경을 지원하지 않습니다. 이 경우에는 다른 접근이 필요합니다.

또한 공용 네트워크 접근을 끈 AI Search를 에이전트 도구로 쓴다면, 새 Foundry 포털에서 에이전트를 만들어야 합니다. 클래식 Foundry 포털의 이전 버전 Agent 서비스에서는 이 시나리오가 지원되지 않습니다.

첫 행이 가장 중요합니다. 아웃바운드 네트워킹은 배포 후 변경할 수 없습니다. 서브넷을 잘못 잡았거나 나중에 격리를 추가하려 해도 방법이 없고, Foundry를 다시 배포해야 합니다. 파일럿 단계에서 임시로 열어 두고 나중에 조이는 접근은 성립하지 않으므로, 처음부터 목표 구성으로 배포하는 편이 낫습니다.

Teams·Microsoft 365 게시 — 공용 네트워크 접근을 끈 상태에서도 에이전트를 Microsoft Teams와 Microsoft 365에 게시할 수 있습니다. 다만 추가 설정이 필요하므로 관련 안내를 함께 참고해야 합니다.

호스티드 에이전트와 컨테이너 레지스트리 — 2026년 6월 25일 이후 만든 프로젝트는 공용 접근을 끄고 프라이빗 엔드포인트를 둔 Azure Container Registry를 지원합니다. 그 이전에 만든 프로젝트는 레지스트리가 공용 엔드포인트로 접근 가능해야 하며, 기존 프로젝트는 영향을 받지 않고 계속 동작합니다. 이미 구성한 사설·가상 네트워크 주입 Foundry를 다시 배포할 필요는 없습니다.

5번을 빠뜨리는 경우가 많습니다 — Foundry 리소스만 격리하고 의존 리소스를 열어 두면 격리가 완성되지 않습니다. Standard 설정에서 지정한 Storage, AI Search, Cosmos DB 각각에 프라이빗 엔드포인트를 만들어야 합니다.
